¿Qué es Spring Security y qué es la cadena de filtros?

Spring Security es la librería de Spring que se encarga de dos preguntas: ¿quién eres? (autenticación) y ¿qué puedes hacer? (autorización).

Funciona como una cadena de filtros: cada petición pasa por una fila de revisiones antes de llegar a tu controlador. Si alguna falla, el controlador ni se entera.

¿Qué es Maven y por qué hay que "refrescar"?

Maven es la herramienta que descarga las librerías que declaras en el pom.xml. Al agregar una, IntelliJ no la ve hasta sincronizar.

Un alumno preguntó cómo: "cuando lo agrega, por aquí le aparece un iconito de Maven, y si no, se va acá y se va a la parte de sincronizar".

@ManyToMany, @JoinTable y tabla puente

Un usuario puede tener varios roles y un rol puede estar en varios usuarios. Eso se llama muchos a muchos, y una base relacional no lo guarda en una sola tabla: hace falta una tercera, la tabla puente, con una fila por cada pareja usuario-rol.

  • @ManyToMany: marca la relación.
  • @JoinTable(name = "UsuarioRol"): nombre de la tabla puente.
  • joinColumns: la columna que apunta a esta entidad (idUsuario).
  • inverseJoinColumns: la que apunta a la otra (idRol).
  • referencedColumnName: a qué columna de la tabla original apunta. Aquí se llaman igual "para no complicarnos la existencia".
¿Qué es @Builder?

Una anotación de Lombok que crea un constructor por pasos: Usuario.builder().userName("ana").email("a@b.com").build(). Evita recordar el orden de los parámetros del constructor largo.

¿Qué es Serializable?

implements Serializable aparece en las dos entidades. Es la misma convención de la clase del 28: marca que el objeto se puede convertir en bytes. No cambia nada de lo que se hace hoy.

public interface UsuarioRepository extends JpaRepository<Usuario, Long> {
    Optional<Usuario> findByUserName(String userName);

"Existe, pues, no, en realidad nosotros lo vamos a crear. Va a ser un método auxiliar que necesitamos y que a lo mejor vamos a ir agregando."
¿Cómo funciona findByUserName si no tiene cuerpo?

Spring Data JPA lee el nombre del método y escribe la consulta: findBy + el nombre del atributo (UserName) significa SELECT ... WHERE nombreUsuario = ?. Por eso el atributo de la entidad se llama userName y el método debe escribirse igual.

Devuelve un Optional porque ese usuario puede no existir.

Bloque 5

UserSecurityService: de tu usuario al usuario de Spring

Spring no conoce la clase Usuario que acabas de crear. Hay que traducirla a lo que sí entiende, un UserDetails.

@Service
public class UserSecurityService implements UserDetailsService {

    @Autowired
    private UsuarioRepository usuarioRepository;

    @Override
    @Transactional(readOnly = true)
    public UserDetails loadUserByUsername(String username) throws UsernameNotFoundException {
        Usuario usuario = usuarioRepository.findByUserName(username)
                .orElseThrow(() -> new UsernameNotFoundException("Usuario no encontrado: " + username));

        List<GrantedAuthority> permisos = new ArrayList<>();
        for (Rol rol : usuario.getRoles()) {
            permisos.add(new SimpleGrantedAuthority("ROLE_" + rol.getNombreRol()));
            if (rol.getNombreRol().equals("admin")) {
                permisos.add(new SimpleGrantedAuthority("EVENTO_CREAR"));
                permisos.add(new SimpleGrantedAuthority("EVENTO_MODIFICAR"));
            } else if (rol.getNombreRol().equals("user")) {
                permisos.add(new SimpleGrantedAuthority("EVENTO_LEER_TODO"));
            }
        }

        return User.builder()
                .username(usuario.getUserName())
                .password(usuario.getPassword())
                .authorities(permisos)
                .accountLocked(usuario.getBloqueado())
                .disabled(usuario.getHabilitado())
                .build();
    }
}
"El user details service no lo escribimos nosotros, ese existe y es parte del ecosistema, del API de security. Y nos dice, entre otras cosas, que tenemos que sobrescribir el método loadUserByUsername."
"Todos los roles que se hayan definido inician con ROLE_ guion bajo [...]. De tal forma que si aquí el rol se llama admin, pues en realidad para que esto funcione debería de ser ROLE_ADMIN."

En pantalla se ve el ciclo for (Rol rol : ...) con las líneas permisos.add(...), el if / else if por nombre de rol y el cierre con return User.builder().... Los nombres de los permisos (EVENTO_CREAR y los demás) los eligió él: "ustedes determinan qué hacer".

!

Dos cabos que dejó, y que al copiar el código fallan.

1. disabled es lo contrario de habilitado. Él lo llenó con getHabilitado() y dijo "yo qué sé, según lo que tengamos". Con habilitado = true, el usuario queda deshabilitado.

2. Los roles se guardan como admin/user en minúsculas, y las reglas de la configuración preguntan por ADMIN/USER. Spring distingue mayúsculas y no hay coincidencia.

¿Qué es un UserDetails y un UserDetailsService?

UserDetails es la ficha que Spring Security usa de cada usuario: nombre, clave, permisos y si la cuenta está bloqueada o deshabilitada. Es parte del núcleo de la librería: "si le pican, dice que tiene una colección de todas las autoridades, del password, del username, de si expiró, si la cuenta está bloqueada...".

UserDetailsService es la interfaz con un solo método, loadUserByUsername: "dame la ficha de este nombre". Tú decides de dónde sale; aquí, de la base.

Authority y role: ¿no son lo mismo?

En Spring Security los dos son un GrantedAuthority, un texto. La diferencia es una convención: si el texto empieza con ROLE_, se puede preguntar con hasRole("ADMIN") (que agrega el prefijo solo). Si no lleva prefijo, se pregunta con hasAuthority("EVENTO_CREAR").

  • Rol: el puesto, general. ROLE_ADMIN.
  • Permiso (authority): una acción concreta. EVENTO_CREAR.
UsernameNotFoundException

La excepción de Spring Security para "ese usuario no existe". Tampoco la escribió él: "también forma parte del core". Su mensaje por defecto es User not found.

Bloque 6

AuthController: quién soy y qué puedo

Un controlador pequeño que le devuelve al cliente (por ejemplo, un Angular en el puerto 4200) quién inició sesión.

@RestController
@RequestMapping("/api/v1/auth")
@CrossOrigin(origins = "http://localhost:4200")
public class AuthController {

    @GetMapping("/perfil")        // el nombre lo eligió "el que ustedes quieran"
    public ResponseEntity<UserSessionDTO> obtenerPerfilDeUsuario(Authentication authentication) {
        String userName = authentication.getName();

        List<String> roles = authentication.getAuthorities().stream()
                .map(GrantedAuthority::getAuthority)
                .filter(a -> a.startsWith("ROLE_"))
                .toList();

        List<String> authorities = authentication.getAuthorities().stream()
                .map(GrantedAuthority::getAuthority)
                .filter(a -> !a.startsWith("ROLE_"))
                .toList();

        return ResponseEntity.ok(new UserSessionDTO(userName, roles, authorities));
    }
}
"Asegúrense que esta cosa sea de tipo org.springframework.security.core, porque, se dieron cuenta, hay un montón de estas cuestiones acá."

Armó la lista de roles primero con filter(... startsWith("ROLE_")). La de permisos la hizo copiando y pegando, "solo que aquí vamos a hacerle algo diferente, vamos a negarlo": el mismo filtro con !.

¿De dónde sale el parámetro Authentication?

Spring lo inyecta solo: si la petición llegó hasta aquí, ya pasó el login, y Authentication trae el nombre del usuario (getName()) y sus permisos (getAuthorities()). No lo creaste tú.

¿Qué es @CrossOrigin y qué es el puerto 4200?

Un navegador bloquea por defecto que una página de un origen (http://localhost:4200) llame a una API de otro (http://localhost:8085). A eso se le llama CORS.

@CrossOrigin(origins = ...) le dice a la API que sí acepte peticiones de ese origen. El 4200 es el puerto de Angular en desarrollo; el profesor lo usa de ejemplo "para un Angular, para un React, para un Vue".

@EnableMethodSecurity

ReglaQué hace

Cabos que dejó este bloque.

1. El método recibe un CorsConfigurationSource pero en la clase nunca se ve el bean que lo crea. Sin él la aplicación no arranca.

2. Para el DELETE pide EVENTO_ELIMINAR, pero el servicio solo le da al admin EVENTO_CREAR y EVENTO_MODIFICAR. Nadie podría borrar.

3. Dijo que faltaba el bean authenticationManager: "si tomaron apuntes, termínenlos, del día de la presentación". Esa clase no la tengo.

4. @EnableMethodSecurity quedó "preparado, por si se requiere un @PreAuthorize", sin usarse.

@Configuration, @Bean y las tres anotaciones @Enable...
  • @Configuration: esta clase solo existe para configurar la aplicación.
  • @Bean: el objeto que devuelve el método se registra en Spring y se puede inyectar donde haga falta.
  • @EnableWebSecurity: activa la seguridad web con tu configuración.
  • @EnableMethodSecurity: permite usar @PreAuthorize("hasRole('ADMIN')") sobre métodos del controlador.
  • @RequiredArgsConstructor: Lombok crea un constructor con los campos final.
CSRF, sesión sin estado y httpBasic
  • CSRF (Cross-Site Request Forgery): un ataque donde otra página hace que tu navegador mande una petición con tu sesión abierta. Se suele deshabilitar en una API que no usa formularios ni cookies de sesión: "vamos a deshabilitarlo, por lo pronto".
  • Sin estado (STATELESS): el servidor no guarda sesión. El cliente manda su usuario y clave en cada petición.
  • httpBasic: el cliente manda el usuario y la clave en una cabecera Authorization, codificados en Base64. Es simple y por eso solo es seguro sobre HTTPS.
¿Qué es BCrypt?

Un algoritmo que convierte la clave en un código que no se puede deshacer, por ejemplo $2a$10$.... En la base se guarda ese código, no la clave real. Cuando alguien inicia sesión, Spring aplica BCrypt a lo que escribió y compara los dos códigos.

El bean passwordEncoder le dice a Spring que use BCrypt. Por eso las claves que pongas en la base deben estar ya convertidas.

¿Qué significa el ERROR 1064 y el error de llave foránea?
  • 1064: error de sintaxis del SQL. Aquí, por usar comillas dobles junto con un carácter de más. En MySQL conviene escribir los textos entre comillas simples.
  • Llave foránea: la tabla puente guarda ids de Usuario y de Rol. MySQL no deja guardar el id 2 de usuario si en Usuario no existe una fila con id 2.
¿Por qué current_date y now()?

La fecha de creación del rol es de tipo datetime (LocalDateTime en Java), y now() trae fecha y hora. El profesor usó current_date y su "fecha actual cuando se crea". Las dos sirven para llenar la columna.

En qué se diferencia este código de lo que quedó en pantalla
  • El nombre del método del controlador y su ruta, /perfil, son míos: él dijo "pongan el nombre que quieran".
  • La mayor parte de SecurityConfig se escribe en pantalla a trozos y la última parte (los bloques de métodos PUT y DELETE) se corta del encuadre. Reconstruí las rutas a partir de lo que dijo.
  • Los INSERT siguen el orden de columnas del diagrama de la clase, que coincide con el orden en que él dictó los valores. El hash de la clave es el que generes.
  • Dejé tal cual los dos errores que marqué (disabled y las mayúsculas del rol), para que veas qué se dijo y qué falla.
