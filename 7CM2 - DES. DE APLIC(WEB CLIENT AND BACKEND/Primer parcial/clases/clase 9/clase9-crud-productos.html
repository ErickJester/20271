Todo lo repetitivo, a mano con el IDE

Antes de usar Lombok, hace la clase completa con el menú Código → Generar. Es la versión larga de lo que luego se resuelve con tres anotaciones.

  1. Constructor sin argumentos: Código → Generar → constructor, y "Select None" para no marcar ningún atributo.
  2. Constructor con todos los atributos: mismo menú, los selecciona todos.
  3. Getters y setters: por separado, o de una vez con "Getters and Setters".
  4. equals() y hashCode(): "a final de cuentas sabemos que el ID es único, que trabaje contra el ID".

¿Por qué equals() y hashCode() solo con el id?

Dos productos se consideran "el mismo" si tienen el mismo id, aunque el nombre o el precio hayan cambiado. Es lo que se espera de una entidad con identificador único. Los dos métodos deben ir juntos: si dos objetos son iguales según equals, tienen que dar el mismo hashCode.

Una lista en memoria como base de datos falsa

No hay base de datos todavía. Los datos son una lista dentro del propio controlador, con cinco productos de ejemplo.

private final List<Producto> productos = new ArrayList<>(List.of(
    new Producto(1L, "Laptop 1", 5000),
    new Producto(2L, "Laptop 2", 6000),
    new Producto(3L, "Laptop 3", 7000)
    // ...hasta 5 productos
));

Copia y pega hasta tener cinco. Luego el IDE marca un error y el profesor le pregunta al grupo cómo corregirlo. Un alumno responde: importando la lista y Producto. Hace falta eso, pero no es lo que rompía:

"Hay que castigarlo... porque es un valor entero y el tipo es Long. Entonces le decimos que es un Long poniéndole una L al final."

¿Por qué 1L y no 1?

El literal 1 es un int, y el constructor pide un Long. Java no convierte solo un int a Long (el objeto envoltorio). Con 1L el literal ya es long y se empaqueta a Long. Con 5000 en el precio no hay problema, porque el campo es double y un entero sí se ensancha a double.

¿Por qué envolver List.of(...) en un new ArrayList<>(...)?

List.of devuelve una lista inmutable: no deja agregar ni quitar. Como el POST va a hacer add y el DELETE va a hacer removeIf, la lista tiene que ser modificable. new ArrayList<>(...) copia los elementos a una lista que sí lo es. El profesor no lo explicó en la clase; lo puso así desde el inicio.

Bloque 8 · minuto 25:26 a 32:00

El error del DataSource

La aplicación no arranca. La consola muestra una excepción y él la usa para explicar por qué.

"Y si les aparece algo como eso... vamos bien. ¿Por qué? Bueno, nos dice que trató de arrancar, no pudo, y nos da una referencia: 'Oye, mira, no has configurado un DataSource'. [...] Pero no estamos usando base de datos. La respuesta es no, pero por el simple hecho de haber agregado la dependencia de Spring Data, hay que configurarlo."

La solución es agregar cuatro propiedades al application.properties:

spring.datasource.url=jdbc:mysql://localhost:3306/bd
spring.datasource.username=root
spring.datasource.password=<la contraseña de tu MySQL>
spring.datasource.driver-class-name=com.mysql.cj.jdbc.Driver

Dictó una contraseña de ejemplo; aquí la dejo como marcador. Vuelve a correr y esta vez Tomcat arranca en el 8083 sin errores.

¿Qué es un DataSource y por qué lo exige Spring Data?

Es el objeto que sabe conectarse a la base de datos: la URL, el usuario, la contraseña y el driver. Al agregar Spring Data JPA, Spring asume que vas a usar una base y trata de crear ese objeto al arrancar. Si no le dices dónde está, se detiene. Por eso da error aunque el código de hoy nunca toque una base.

Cada propiedad: url es la dirección de la base (servidor, puerto 3306 y nombre bd); username y password son las credenciales; driver-class-name es la clase Java del conector de MySQL.

"En teoría ya tenemos conectado Spring con la base de datos... aunque la base no exista todavía. Si les corrió, literal, es porque algo hicieron mal."

i

Dos notas mías sobre esto. La última frase parece hablar de quien arrancó sin error antes de configurar el DataSource: sin la dependencia de Data, no habría error. Y sobre "aunque la base no exista": con JPA y MySQL, Spring suele intentar conectarse al arrancar. Si a ti te truena porque no hay un MySQL corriendo o la base bd no existe, no es un error tuyo; lo más probable es que él sí tuviera uno activo. Otra salida, que él no mencionó, es quitar la dependencia de Data mientras no la uses.

Bloque 10 · minuto 36:51 a 45:20

Segundo endpoint: buscar por id

Empieza por probar la ruta antes de programarla, para ver el 404, y luego escribe el método.

Duplica el request anterior, lo llama Mostrar un producto y agrega /2 a la URL. La respuesta es un 404 Not Found. "Tiene sentido porque no lo hemos programado."

Regresa al código y escribe el método:

@GetMapping("/{id}")
public ResponseEntity<Producto> mostrarProducto(@PathVariable Long id) {
    Optional<Producto> producto = productos.stream()
        .filter(p -> p.getId().equals(id))
        .findFirst();
    if (producto.isPresent()) {
        return ResponseEntity.ok(producto.get());
    } else {
        return ResponseEntity.notFound().build();
    }
}

Guarda, reinicia el servidor y prueba: el id 2 devuelve 200 OK con la Laptop 2. El id 30, que no existe, devuelve 404 Not Found. "Funciona."

¿Qué es @PathVariable y en qué se distingue de @RequestParam?

@PathVariable toma un valor que va dentro de la ruta: en /productos/2, el 2 es el {id}. @RequestParam, de la clase 8, toma un valor que va después del signo de interrogación: ?valor=10. Por eso aquí el @GetMapping lleva "/{id}" entre llaves y allá no.

¿Qué hace ese stream().filter(...).findFirst() y qué es un Optional?

Recorre la lista, se queda solo con los productos cuyo id coincide con el pedido, y toma el primero. Como puede que no haya ninguno, el resultado no es un Producto sino un Optional<Producto>: una caja que puede tener el producto o estar vacía. Con isPresent() se pregunta si la caja trae algo, y con get() se saca.

"Si no, devuélveme un ResponseEntity.notFound().build()."

Tercer endpoint: crear un producto

El bloque más largo. Escribe el método y prueba el envío con un cuerpo JSON.

Dice "ya vamos tres de cinco métodos. Hace falta el PUT y el POST". Escribe primero el POST, sin cambiar la ruta:

@PostMapping
public ResponseEntity<Producto> crearProducto(@RequestBody Producto producto) {
    productos.add(producto);
    return ResponseEntity
        .created(URI.create("/api/v1/productos/" + producto.getId()))
        .body(producto);
}

El producto no se guarda en ninguna base: solo se agrega a la lista en memoria. Devuelve un 201 Created, con la ruta del nuevo recurso y el objeto en el cuerpo.

¿Qué hace @RequestBody?

Toma el cuerpo de la petición, que llega como JSON, y lo convierte en un objeto Producto haciendo coincidir los nombres de los campos (id, nombre, precio). Es lo que usan POST y PUT para recibir datos, porque un GET no lleva cuerpo.

En Insomnia clona la petición, cambia el verbo a POST, elige el tipo JSON y escribe el cuerpo "de lo que modelé":

{
  "id": 6,
  "nombre": "Laptop 6",
  "precio": 15000
}

Al enviar responde 201 Created. Vuelve a "Mostrar lista" y el producto 6 ya está. "Mientras la aplicación no se detenga, ahí va a estar."

i

Es el "happy path" de la clase 7, otra vez. Este POST no valida nada: si mandas otro producto con id 6, lo agrega de nuevo y responde 201. Tampoco hay manejo de errores, que es justo lo que el profesor pidió controlar a mano. Aquí no lo hace porque es un ejemplo; en tu proyecto sí tendrías que.

Cuarto endpoint: eliminar, y cierre

El último método de la clase y el cierre. El PUT queda en el aire.

@DeleteMapping("/{id}")
public ResponseEntity<Void> eliminarProducto(@PathVariable Long id) {
    productos.removeIf(p -> p.getId().equals(id));

"No quiero que me devuelva nada", así que responde 204 No Content. Por eso el tipo de retorno es ResponseEntity<Void>: no hay cuerpo.

"A final de cuentas estamos jugando con los métodos. Faltaría el PUT para actualizar, pero ya es la misma lógica. Sería todo por el día de hoy, no les doy más lata."

Otra nota mía. Este DELETE devuelve 204 aunque el id no exista, porque removeIf no falla cuando no encuentra nada. Es la misma limitación de "happy path" de arriba.

import com.ipn.mx.modelo.Producto;
import java.net.URI;
import java.util.ArrayList;
import java.util.List;
import java.util.Optional;
import org.springframework.http.ResponseEntity;
import org.springframework.web.bind.annotation.*;

@RestController
@RequestMapping("/api/v1/productos")
public class ProductoController {

    private final List<Producto> productos = new ArrayList<>(List.of(
        new Producto(1L, "Laptop 1", 5000),
        new Producto(2L, "Laptop 2", 6000),
        new Producto(3L, "Laptop 3", 7000),
        new Producto(4L, "Laptop 4", 8000),
        new Producto(5L, "Laptop 5", 9000)
    ));

    @GetMapping
    public ResponseEntity<List<Producto>> listarProductos() {
        return ResponseEntity.ok(productos);
    }

    @GetMapping("/{id}")
    public ResponseEntity<Producto> mostrarProducto(@PathVariable Long id) {
        Optional<Producto> producto = productos.stream()
            .filter(p -> p.getId().equals(id))
            .findFirst();
        if (producto.isPresent()) {
            return ResponseEntity.ok(producto.get());
        } else {
            return ResponseEntity.notFound().build();
        }
    }

    @PostMapping
    public ResponseEntity<Producto> crearProducto(@RequestBody Producto producto) {
        productos.add(producto);
        return ResponseEntity
            .created(URI.create("/api/v1/productos/" + producto.getId()))
            .body(producto);
    }

    @DeleteMapping("/{id}")
    public ResponseEntity<Void> eliminarProducto(@PathVariable Long id) {
        productos.removeIf(p -> p.getId().equals(id));
        return ResponseEntity.noContent().build();
    }
