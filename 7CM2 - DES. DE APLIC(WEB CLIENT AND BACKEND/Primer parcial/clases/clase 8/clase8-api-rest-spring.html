¿Qué son groupId, artifactId y Maven?

Maven es la herramienta que descarga las dependencias y construye el proyecto a partir del archivo pom.xml. El groupId identifica a quien lo hace, normalmente con el dominio al revés (com.ipn.mx). El artifactId es el nombre del proyecto. Juntos son la "dirección" con la que se identifica el proyecto.

JAR, WAR, EAR y RAR

Explicó los cuatro tipos de empaquetado de Java:

  • .jar (Java Archive): lo típico para aplicaciones de escritorio y de consola, un ejecutable.
  • .war (Web Application Archive): para web. Se mete en la carpeta correspondiente de un Tomcat, un TomEE, un GlassFish o un Payara y se carga.
  • .ear (Enterprise Application Archive): para módulos empresariales con EJB. Si no se separan los proyectos por parte, todo se empaqueta en un JAR o en un WAR "y tampoco pasa nada".
  • .rar (Resource Adapter Archive): "no es el ZIP tradicional", vive en el ecosistema empresarial y "rara vez se utiliza". Es para recursos.

"Por definición aquí solo tenemos dos archivos: JAR o WAR. ¿Funcionan muy similar? Sí y no. El JAR lo que trae incrustada es una versión muy minimalista de un Tomcat, Tomcat embebido. Por eso puede funcionar."

¿Qué es EJB?

Enterprise JavaBeans: la tecnología empresarial de Java para componentes de lógica de negocio que corren dentro de un servidor de aplicaciones. El profesor solo lo nombró para explicar cuándo tiene sentido un EAR.

properties o yml

Los dos hacen lo mismo. El YAML se organiza por sangría: empiezas con el elemento principal y vas bajando según la propiedad. Comentó que a quien viene de Python le resulta natural, y que a él le cuesta. Aquí usa properties.

¿Cómo se ve la misma propiedad en cada formato?
# application.properties
server.port=8082

# application.yml
server:
  port: 8082

En YAML cada nivel del nombre baja una línea y una sangría. Un espacio de más o de menos cambia a qué elemento pertenece la clave. El profesor lo llamó "tabuladores", pero en YAML la sangría debe ser con espacios.

El DTO, el controlador y el primer endpoint

Es el bloque más largo y el centro de la clase. Va de tres paquetes vacíos a un método que responde en el navegador.

El DTO, como record

"Nos dicen que un DTO es una clase Java simple que probablemente implemente la interfaz de serialización, que tenga atributos privados a la clase, un constructor con argumento cero... ¡Ya me acordé qué otra cosa me hacía falta! Se me olvidó poner Lombok para no escribir cosas."

En lugar de una clase común, usa un record, "porque esta cosa no va a cambiar". Lo llama ConversionResponse, lo quiere "para respuesta", y lo crea en un paquete dto:

package com.ipn.mx.dto;

public record ConversionResponse(
    Double valorOriginal,
    String unidadOriginal,
    Double valorRespuesta,
    String unidadRespuesta
) {}

Podría ser una clase, con getters y setters para cada campo. Este es "literal, un objeto que funciona simplemente pasándole valores a los atributos y recuperando los valores". Es inmutable, y por eso le queda bien a un DTO.

¿Qué es un record y qué gano con él?

Una forma corta de declarar una clase de datos. Escribes solo los campos entre paréntesis y Java genera el constructor, los métodos de lectura, equals, hashCode y toString. Sus campos no se pueden cambiar después de creado el objeto (es inmutable), y no hay setters.

Para un DTO de respuesta es justo lo que hace falta: se arma una vez, se manda y no se toca. Necesita Java 16 o superior, por eso conecta con el mínimo de 17 de antes.

El controlador

Nuevo paquete controller, nueva clase TemperaturaController. Dos anotaciones sobre la clase:

  • @RestController: "porque vamos a crear un API". Al ser REST, "debería de permitirnos utilizar todos los verbos del protocolo".
  • @RequestMapping("/api/temperatura"): "tengo que encontrar la forma para llegar a este cuate". Es la ruta base de todo lo que tenga dentro.
@RestController
@RequestMapping("/api/temperatura")
public class TemperaturaController {

}

Con eso ya se sabe cómo empieza cualquier URL de la API. Y aquí llega la pieza que ordena la clase: cada pedazo de la URL sale de una línea concreta.

http://localhost:8082/api/temperatura/convertir-a-fahrenheit?valor=10
Servidor y puerto. El puerto viene de server.port en application.properties. El host es donde corre el servidor: "mi localhost, mi 127.0.0.1, mi 192.168.x.x", o el nombre si hay DNS.
Ruta base. El @RequestMapping de la clase.
Nombre del método. El @GetMapping de cada método.
Parámetro. El @RequestParam, que llega después del signo de interrogación.

"Cualquier cosa que nosotros vayamos a solicitar a la URL tenemos que pegar esto de arranque, hasta ahí. ¿De dónde sale? De este archivito. [...] Y el resto lo obtenemos justo de la definición del RequestMapping en el controller."

¿Qué es localhost y por qué da lo mismo que 127.0.0.1?

localhost es el nombre que tu propia máquina se da a sí misma; se traduce a la dirección 127.0.0.1. Si el servidor corre en la misma computadora que el navegador, apuntas ahí. Si corriera en otra, pondrías su IP (como 192.168.x.x en una red local) o su nombre de dominio.

El primer método: Celsius a Fahrenheit

Solo hace falta un verbo, @GetMapping, porque "no vamos a insertar, no vamos a actualizar, no vamos a eliminar". La idea es: "método fulanito, te paso un argumento, opera con él y devuélveme un resultado".

El método es público, devuelve un ResponseEntity de ConversionResponse y se llama celsiusToFahrenheit. Recibe el parámetro valor como Double, guardado en una variable celsius:

@GetMapping("/convertir-a-fahrenheit")
public ResponseEntity<ConversionResponse> celsiusToFahrenheit(
    @RequestParam(name = "valor") Double celsius
) {
    Double fahrenheit = (celsius * 9 / 5) + 32;
    ConversionResponse response = new ConversionResponse(celsius, "°C", fahrenheit, "°F");
    return ResponseEntity.ok(response);
}

Los argumentos del constructor van en el orden del record: valor original (celsius), unidad original ("°C"), valor de la respuesta (fahrenheit) y unidad de la respuesta ("°F").

¿Qué hace @RequestParam?

Le dice a Spring que tome un valor de los parámetros de la URL, los que van después del ?. Con name = "valor" busca ?valor=... y lo convierte al tipo que declares, aquí Double. El nombre de la variable de Java (celsius) puede ser distinto del nombre del parámetro (valor).

"Tomen ustedes una decisión: ¿le van a poner nombre o simplemente se van a referir a esto? Cada método que ustedes mapeen puede llevar un nombre en particular. [...] Como son puros GET, sí hay que diferenciarlos: eventualmente o reciben un argumento o tienen un nombre. En este caso lo más sano es ponerle un nombre."

¿Por qué dos @GetMapping sin nombre chocarían?

Si dos métodos responden al mismo verbo y a la misma ruta, Spring no sabe a cuál mandar la petición y falla al arrancar. Con un nombre distinto en cada @GetMapping (/convertir-a-fahrenheit, /convertir-celsius-a-kelvin) cada uno tiene su propia ruta.

i

ResponseEntity desde el primer método. En la clase anterior el profesor dijo que la entidad no debe regresarse sola, sino dentro de un ResponseEntity. Aquí es lo primero que hace. ResponseEntity.ok(response) devuelve el objeto con código 200.

Copió el método anterior y lo fue ajustando. "Ya rezongó" es el IDE marcando error cada vez que cambia algo a medias; se arregla al terminar de renombrar. Cambió la variable a kelvin, la operación a celsius + 273.15 y la unidad de respuesta a "K". Como ya no hay operación extra, "hasta le podemos quitar ese paréntesis".

@GetMapping("/convertir-celsius-a-kelvin")
public ResponseEntity<ConversionResponse> celsiusToKelvin(
    @RequestParam(name = "valor") Double celsius
) {

    ConversionResponse response = new ConversionResponse(celsius, "°C", kelvin, "K");
    return ResponseEntity.ok(response);
}

El mismo DTO, como clase con Lombok

Respondió a "¿y si quiero una clase en lugar de un record?": por supuesto que se puede.

package com.ipn.mx.dto;

import lombok.Data;
import lombok.NoArgsConstructor;
import lombok.AllArgsConstructor;
import lombok.Builder;
import java.io.Serializable;

@Data
@NoArgsConstructor
@AllArgsConstructor
@Builder
public class ConversionResponse implements Serializable {
    private Double valorOriginal;
    private String unidadOriginal;
    private Double valorRespuesta;
    private String unidadRespuesta;
}

El clásico implements Serializable, y con Lombok: @Data, @NoArgsConstructor, @AllArgsConstructor "y, ¿por qué no?, @Builder". Cuatro atributos privados, y ya. El controlador "ni siquiera cambiaría": debería funcionar igual.

¿Qué hace cada anotación de Lombok?
  • @Data: genera getters, setters, toString, equals y hashCode.
  • @NoArgsConstructor: el constructor sin argumentos.
  • @AllArgsConstructor: el constructor con todos los campos.
  • @Builder: permite armar el objeto paso a paso con el patrón Builder.
i

Dos cosas que conectan, dichas por mí y no por el profesor. Primero: para usar esta versión hay que agregar la dependencia de Lombok al proyecto, y en el asistente del bloque 1 no se marcó. Con el record no hace falta. Segundo: @Builder es el patrón Builder que dejó de investigación en la clase 5 ("qué es, para qué sirve, con qué se come"). Aquí lo tienes en un ejemplo real.

package com.ipn.mx.controller;

import com.ipn.mx.dto.ConversionResponse;
import org.springframework.http.ResponseEntity;
import org.springframework.web.bind.annotation.GetMapping;
import org.springframework.web.bind.annotation.RequestMapping;
import org.springframework.web.bind.annotation.RequestParam;
import org.springframework.web.bind.annotation.RestController;

@RestController
@RequestMapping("/api/temperatura")
public class TemperaturaController {

    @GetMapping("/convertir-a-fahrenheit")
    public ResponseEntity<ConversionResponse> celsiusToFahrenheit(
        @RequestParam(name = "valor") Double celsius
    ) {
        Double fahrenheit = (celsius * 9 / 5) + 32;
        ConversionResponse response = new ConversionResponse(celsius, "°C", fahrenheit, "°F");
        return ResponseEntity.ok(response);
    }

    @GetMapping("/convertir-celsius-a-kelvin")
    public ResponseEntity<ConversionResponse> celsiusToKelvin(
        @RequestParam(name = "valor") Double celsius
    ) {
        Double kelvin = celsius + 273.15;
        ConversionResponse response = new ConversionResponse(celsius, "°C", kelvin, "K");
        return ResponseEntity.ok(response);
    }

    // Tarea: F a C, F a K, K a C y K a F
}
