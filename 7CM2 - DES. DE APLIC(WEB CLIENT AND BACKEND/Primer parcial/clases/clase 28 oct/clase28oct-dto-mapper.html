El valor de DB_URL es lo único que escribió en el pizarrón, con "servidor" anotado debajo de localhost:

jdbc:bd://localhost:puerto/bd        <- como quedó en el pizarrón
jdbc:postgresql://localhost:5432/nombreBD   <- como lo dictó
"Son pares nombre-valor. [...] Y san se acabó. Literal, así como está ahí, pero hay que meterlo acá."

Probó en local y el puerto 8084 estaba ocupado: "ya no me quiero pelear con ese puerto, no sé quién lo tiene en uso, pero vamos a decirle que sí" (en IntelliJ, aceptar que arranque igual). Con eso la conexión salió satisfactoria y pasó a lo siguiente.

Qué significa cada línea de application.properties
  • server.port=8084: el número de puerta por donde la aplicación recibe peticiones. Si otro programa ya usa esa puerta, no arranca (el choque que tuvo en clase).
  • ${DB_URL}: "toma el valor de la variable de entorno que se llama DB_URL". Las llaves con $ son la forma de pedirle un valor al sistema.
  • jdbc:postgresql://localhost:5432/nombreBD: jdbc es la tecnología de Java para hablar con bases de datos; postgresql es el motor; localhost es "esta misma computadora"; 5432 es la puerta del motor; nombreBD es la base dentro del motor.
  • ddl-auto=update: al arrancar, Hibernate crea las tablas que falten y agrega columnas nuevas, sin borrar los datos que ya hay.
  • show-sql=true: imprime en la consola cada SQL que Hibernate ejecuta. Sirve para ver qué hace por detrás.
  • springdoc...enabled=true: enciende la documentación automática de la API (Swagger), una página donde se ven y se prueban los endpoints.
¿Qué es una variable de entorno y dónde se define?

Un par nombre-valor que vive en el sistema operativo o en la configuración de ejecución, fuera del código. Spring la lee con ${NOMBRE}.

En IntelliJ se agregan en Run → Edit Configurations → Environment variables. Así la contraseña de la base no queda en el repositorio.

DTO · entrada con validaciones
package com.ipn.mx.evento.dto;

import jakarta.validation.constraints.FutureOrPresent;
import jakarta.validation.constraints.NotBlank;
import jakarta.validation.constraints.NotNull;
import jakarta.validation.constraints.Size;
import java.time.LocalDate;

public record CreateOrUpdateEventoDTO(
        @NotBlank(message = "El nombre del evento no debe estar vacío")
        @Size(min = 4, max = 200, message = "El nombre del evento debe tener entre 4 y 200")
        String nombreEvento,

        @NotBlank(message = "La descripción del evento no debe estar vacía")
        @Size(min = 4, max = 500, message = "La descripción del evento debe tener entre 4 y 500")
        String descripcionEvento,

        @NotNull(message = "La fecha es obligatoria")
        @FutureOrPresent(message = "La fecha del evento debe ser hoy o en el futuro")
        LocalDate fechaCreacion
) {
}

Primero lo llamó CreateEventoDTO; después le cambió el nombre (Refactor → Rename) a CreateOrUpdateEventoDTO porque el mismo objeto sirve para insertar y para actualizar.

"Va a tener lo mismo, pero me va a servir para el update. [...] A menos que ustedes decidan lo contrario. Si a la mejor dices: la fecha de creación en una actualización no la voy a hacer cambiar, la puedo quitar."

Sin idEvento: es autogenerado, así que al crear no se manda. La única validación nueva es la de fecha:

"No puedo registrar un evento que pasó ayer, inclusive que pasó hace unos cuantos minutos."
¿Por qué record y no una clase con Lombok?

Un record es una clase inmutable que ya trae constructor, equals, hashCode, toString y un método por campo con el mismo nombre del campo.

Por eso no hay getX() ni setX(): se lee dto.nombreEvento(). El profesor lo repite varias veces durante el mapper y el correo.

¿Qué hace @FutureOrPresent?

Acepta fechas de hoy en adelante y rechaza las pasadas. Es de jakarta.validation, igual que @NotBlank, @NotNull y @Size.

La validación corre cuando llega la petición al controlador, no después (ver Bloque 6).

¿Qué es un DTO y por qué "encapsular" los objetos de negocio?

DTO significa Data Transfer Object: un objeto que solo sirve para llevar datos de un lugar a otro, sin lógica. Es la "caja de envío" entre el cliente y tu aplicación.

"Encapsular los objetos de negocio" quiere decir no mostrar hacia afuera la entidad real (la que está ligada a la tabla). Si la mostraras, cualquier cambio en la tabla cambiaría lo que ve el cliente, y el cliente podría mandarte campos que no debería (por ejemplo, un id).

Qué hace cada anotación del DTO de entrada
  • @NotBlank: el texto no puede ser nulo, ni vacío, ni solo espacios.
  • @NotNull: el valor no puede ser nulo. Se usa en la fecha porque @NotBlank solo vale para textos.
  • @Size(min = 4, max = 200): el texto debe medir entre 4 y 200 caracteres.
  • message = "...": el texto del error que verá el cliente cuando esa regla falle.
  • @FutureOrPresent: la fecha debe ser hoy o posterior.
  • LocalDate: una fecha sin hora (año, mes y día).
  • Long con mayúscula: un número entero que además puede ser null. Con long minúscula nunca podría estar vacío, y antes de guardar el evento no tiene id todavía.
Qué significa import y jakarta.validation

import trae una clase de otro paquete para poder usarla por su nombre corto. jakarta.validation.constraints es el paquete estándar de Java que contiene las anotaciones de validación.

Una anotación es una etiqueta que empieza con @ y le avisa a una librería (aquí, la de validación) qué hacer con ese campo.

La entidad se queda solo con la tabla

Todo lo que era validación se fue a CreateOrUpdateEventoDTO. En Evento quedan los @Column y nada más.

@Entity(name = "Evento")
public class Evento implements Serializable {

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long idEvento;

    @Column(name = "nombreEvento", length = 200, nullable = false, unique = true)
    private String nombreEvento;

    @Column(name = "descripcionEvento", length = 500, nullable = false)
    private String descripcionEvento;

    @Column(name = "fechaCreacion", nullable = false)
    private LocalDate fechaCreacion;
}
"Ahora sí mi clase entidad representa a lo que tengo en mi estructura [...]. Agarra el nombre, dice que por acá se llama nombre de evento, que tiene una longitud de 200, que es no nulo y que es único. Sansacabó. Los demás [validadores] no van ahí."

En el DTO también quitó los @Column y el @Id: ahí no tienen sentido.

"Este cuate representa a una entidad en una base de datos. Este cuate representa a una clase simple en el orientado a objetos."
Qué significa cada anotación de la entidad
  • @Entity(name = "Evento"): "esta clase representa una tabla". El name es el nombre con el que JPA la conoce.
  • @Id: este campo es la llave primaria, el dato que identifica a cada fila.
  • @GeneratedValue(strategy = GenerationType.IDENTITY): el número del id lo asigna la propia base de datos (autonumérico). Por eso al crear no se manda.
  • @Column(name = "nombreEvento", length = 200, nullable = false, unique = true): name es el nombre de la columna; length es el largo máximo del texto; nullable = false significa que la columna es obligatoria; unique = true significa que no puede haber dos eventos con el mismo nombre.
  • implements Serializable: marca que los objetos de esta clase se pueden convertir en una secuencia de bytes. Es una convención habitual en entidades; no cambia lo que se hizo en clase.
JPA, Hibernate y "entidad": ¿cómo se llevan?

JPA es la especificación (las reglas) para guardar objetos Java en una base relacional. Hibernate es la librería que de verdad lo hace. Spring Data JPA pone encima el Repository, con métodos ya hechos como findAll y save.

Una entidad es la clase que JPA liga a una tabla: cada objeto es una fila y cada atributo es una columna.

EventoMapper: el pase de atributos, a mano

Nuevo paquete mapper, clase simple con métodos estáticos. "El que quieran, y así hay varios", dijo del mapeo automático (menciona ModelMapper y MapStruct), "solo que hoy lo vamos a hacer a manita, porque este es más de configuración".

"En algún punto tenemos que decirle: tú vas a hacer este y tú vas a hacer este. Tenemos que hacer el pase de los atributos, hay que hacer un mapeo. Esa les toca a ustedes."
package com.ipn.mx.evento.mapper;

public class EventoMapper {

    // Entity Class ==> Clase DTO
    public static EventoDTO convertirADTO(Evento evento) {
        if (evento == null) {
            return null;
        }
        return new EventoDTO(
                evento.getIdEvento(),
                evento.getNombreEvento(),
                evento.getDescripcionEvento(),
                evento.getFechaCreacion()
        );
    }

    // DTO ==> Entity
    public static Evento convertirEntity(CreateOrUpdateEventoDTO dto) {
        if (dto == null) {
            return null;
        }
        Evento evento = new Evento();
        evento.setNombreEvento(dto.nombreEvento());
        evento.setDescripcionEvento(dto.descripcionEvento());
        evento.setFechaCreacion(dto.fechaCreacion());
        return evento;
    }

    // DTO ==> Entity para un update
    public static void actualizarAPartirDeDTO(CreateOrUpdateEventoDTO dto, Evento evento) {
        if (dto == null || evento == null) {
            return;
        }
        evento.setNombreEvento(dto.nombreEvento());
        evento.setDescripcionEvento(dto.descripcionEvento());
        evento.setFechaCreacion(dto.fechaCreacion());
    }

    public static List<EventoDTO> convertirAListaDTO(List<Evento> eventos) {
        if (eventos == null) {
            return List.of();
        }
        return eventos.stream().map(EventoMapper::convertirADTO).toList();
    }
}

Cuatro métodos, y para cada uno dijo en qué momento se usa:

MétodoRecibeDevuelvePara qué
convertirADTOEventoEventoDTOPintar el resultado de un select * o de un find.
convertirEntityCreateOrUpdateEventoDTOEventoInsertar. No lleva id: lo genera la base ("ese lo vamos a tomar de este cuate").
actualizarAPartirDeDTODTO + EventovoidActualizar. Ya tienes el Evento encontrado por id; solo le pasas los valores nuevos.
convertirAListaDTOList<Evento>List<EventoDTO>La consulta devuelve lista de entidades; se trata como lista de DTO con stream().map(...).
"Recibiste un cuadrito, trátalo como circulito."

¿Por qué se llaman sin crear un objeto EventoMapper?

Porque son static: "el que podamos usar esto es porque los dejé como estáticos, tenía hueva". Si no lo fueran, habría que inyectar o instanciar el mapper (con Spring sería un @Component).

¿Qué es EventoMapper::convertirADTO dentro de map?

Una referencia a método: le dice al stream "aplícale este método a cada elemento". Equivale a e -> EventoMapper.convertirADTO(e).

Qué significa static, void y null en el mapper
  • public static: el método pertenece a la clase, no a un objeto. Se llama escribiendo EventoMapper.convertirADTO(...), sin new.
  • void: el método no devuelve nada; solo hace algo. actualizarAPartirDeDTO modifica el Evento que recibe.
  • if (dto == null) return null;: protege de que llegue un objeto vacío. Si no, la siguiente línea reventaría con un NullPointerException.
  • new Evento(): crea un objeto vacío de la entidad, al que luego se le asignan los valores con setNombreEvento(...) y los demás setters.
  • dto.nombreEvento(): así se lee un campo de un record. En una clase normal sería getNombreEvento().
Cómo leer eventos.stream().map(EventoMapper::convertirADTO).toList()
  1. eventos.stream(): convierte la lista en una cinta de elementos que se pueden procesar uno por uno.
  2. .map(...): aplica una transformación a cada elemento de la cinta. Aquí, convertir cada Evento en EventoDTO.
  3. EventoMapper::convertirADTO: "usa este método"; los dos puntos dobles son una referencia a método.
  4. .toList(): junta los resultados en una lista nueva.

Equivale a un for que recorre la lista, convierte cada elemento y lo mete en otra lista, pero en una línea.

¿Qué es "mapear" y qué es un ORM?

Mapear es copiar los datos de un objeto a otro de otro tipo, campo por campo. Aquí, de Evento a EventoDTO y al revés.

En la clase 10 vimos ORM (Object Relational Mapping): lo mismo, pero entre objetos y tablas. Librerías como ModelMapper o MapStruct hacen el mapeo entre clases automáticamente; hoy se hizo a mano para ver qué pasa.

@Override

@Override
@Transactional(readOnly = true)

@Transactional
public EventoDTO save(CreateOrUpdateEventoDTO dto) {

@Override
@Transactional
public EventoDTO update(Long id, CreateOrUpdateEventoDTO dto) {

            .orElseThrow(() -> new EntityNotFoundException(

¿Y el ControllerAdvice que mencionó?

Dijo que lo ideal sería "una clase específica que se encargue del manejo de las excepciones según la entidad" y "otro controlador [...] que se encargue de estar monitoreando todo el manejo de excepciones, que es un @ControllerAdvice". No lo hicieron: "lo vamos a trabajar normalito en el mismo esquema", con try/catch en cada método.

¿orElse u orElseThrow?

findById devuelve un Optional. orElseThrow(() -> ...) lanza la excepción si está vacío y entrega el valor si no. El -> es una expresión lambda que construye la excepción solo cuando hace falta.

Interfaz e implementación: ¿por qué son dos archivos?

EventoService (interfaz) solo lista qué se puede hacer: los nombres y los tipos de cada método. EventoServiceImpl dice cómo se hace. El controlador solo conoce la interfaz, así que se puede cambiar la implementación sin tocarlo.

@Override avisa que ese método cumple con uno de la interfaz. Si el nombre o los tipos no coinciden, el compilador marca error. Por eso, al cambiar la interfaz, aparecieron errores en la implementación.

Qué hacen findAll, findById, save y delete del repositorio
  • findAll(): trae todas las filas como una lista de Evento.
  • findById(id): busca una fila por su id y la devuelve dentro de un Optional.
  • save(evento): si el Evento no tiene id, hace un INSERT; si ya tiene id, hace un UPDATE. Devuelve la entidad guardada.
  • delete(evento): borra la fila de ese objeto. deleteById(id) hacía lo mismo pasándole solo el id.
Cómo leer .orElseThrow(() -> new EntityNotFoundException(...))

Optional es una caja que puede traer un valor o estar vacía. findById la usa porque el id puede no existir.

orElseThrow dice: "si la caja trae un valor, dámelo; si está vacía, lanza esta excepción". El () -> ... es una lambda: una receta que solo se ejecuta si de verdad hace falta crear la excepción.

EntityNotFoundException significa "no encontré esa entidad". El controlador la atrapa y responde 404.

¿Qué hace @Transactional?

Agrupa todo lo que hace el método en una sola transacción: o todo se guarda, o, si algo falla a la mitad, se deshace todo.

readOnly = true avisa que ese método solo lee, así que la base puede trabajar más ligera.

El controlador: cada resultado con su código HTTP

Los métodos devuelven ResponseEntity para poder elegir el código de estado. En clase los fue cambiando uno por uno.

@GetMapping("/eventos")
public ResponseEntity<List<EventoDTO>> lista() {
    List<EventoDTO> eventos = eventoService.findAll();
    if (eventos.isEmpty()) {
        return ResponseEntity.noContent().build();      // 204
    }
    return ResponseEntity.ok(eventos);                  // 200
}

@GetMapping("/eventos/{id}")
public ResponseEntity<?> findById(@PathVariable Long id) {
    Map<String, Object> respuesta = new HashMap<>();
    try {
        EventoDTO evento = eventoService.findById(id);
        return ResponseEntity.ok(evento);                                     // 200
    } catch (EntityNotFoundException e) {
        respuesta.put("mensaje", e.getMessage());
        return new ResponseEntity<>(respuesta, HttpStatus.NOT_FOUND);          // 404
    } catch (DataAccessException e) {
        respuesta.put("mensaje", "Error al realizar la consulta");
        respuesta.put("error", e.getMessage());
        return new ResponseEntity<>(respuesta, HttpStatus.INTERNAL_SERVER_ERROR); // 500
    }
}

        eventoNuevo = eventoService.save(dto);
        emailService.enviarCorreo(eventoNuevo);
    } catch (DataAccessException e) {
        respuesta.put("mensaje", "Error al realizar el insert en la base de datos");
        respuesta.put("error", e.getMessage());
        return new ResponseEntity<>(respuesta, HttpStatus.INTERNAL_SERVER_ERROR);
    }
    respuesta.put("mensaje", "El evento se ha creado con éxito");
    respuesta.put("evento", eventoNuevo);
    return new ResponseEntity<>(respuesta, HttpStatus.CREATED);                  // 201
}
"Se valida justo cuando llega al controller que espera recibir esas cosas, no hasta después, como estaban."

Lo que recibe el controlador desde Angular, React o lo que sea es un CreateOrUpdateEventoDTO en JSON; ese objeto es el que se valida contra las anotaciones del record.

El correo: dos formas de dejarlo

Tal como quedó, enviarCorreo está dentro del mismo try que el save. Si falla el correo, el cliente recibe un 500 aunque el evento ya se guardó. Propuso, como opción "que determinan ustedes", sacarlo a su propio bloque:

try {
    emailService.enviarCorreo(eventoNuevo);
} catch (MailException e) {
    log.warn("No se pudo enviar el correo del evento {}", eventoNuevo.idEvento(), e);
}

Con @Slf4j arriba de la clase (Simple Logging Facade for Java, ya incluido en Spring Boot). Así el evento se creó y solo el correo falló, y la respuesta sigue siendo 201.

Recorrido línea por línea del create
  1. @PostMapping("/eventos"): este método atiende las peticiones POST a la ruta /eventos.
  2. @Valid @RequestBody CreateOrUpdateEventoDTO dto: toma el JSON del cuerpo de la petición, lo convierte al record y revisa las validaciones antes de entrar al método.
  3. BindingResult resultados: guarda lo que salió de esa revisión. Siempre va justo después del parámetro con @Valid.
  4. Map<String, Object> respuesta = new HashMap<>(): un diccionario clave-valor para armar la respuesta. Spring lo convierte a JSON, por ejemplo {"mensaje": "..."}.
  5. if (resultados.hasErrors()): ¿alguna validación falló? Si sí, arma la lista de errores y responde 400 sin tocar la base.
  6. getFieldErrors().stream().map(...).collect(Collectors.toList()): recorre cada campo con error, arma un texto como "El campo nombreEvento ..." y junta los textos en una lista.
  7. try { ... } catch (DataAccessException e): intenta guardar; si la base falla (conexión caída, tabla inexistente, nombre repetido), cae al catch y responde 500.
  8. eventoService.save(dto): manda el DTO al servicio y recibe el evento ya guardado, con su id.
  9. emailService.enviarCorreo(eventoNuevo): avisa por correo del evento nuevo.
  10. new ResponseEntity<>(respuesta, HttpStatus.CREATED): devuelve el cuerpo y el código 201.
¿Qué es ResponseEntity y qué significa <?>?

ResponseEntity es la respuesta HTTP completa: el código de estado (200, 404...) más el cuerpo. Con ella tú eliges el código, en lugar de dejar que Spring ponga siempre 200.

ResponseEntity<?>: el signo ? es un comodín que significa "cualquier tipo". Se usa cuando el método a veces devuelve un EventoDTO y a veces un Map de error.

HttpStatus.NOT_FOUND, CREATED, BAD_REQUEST son nombres con los que Spring escribe los códigos 404, 201 y 400.

¿Qué hacen @PathVariable, @GetMapping y compañía?
  • @GetMapping, @PostMapping, @PutMapping: ligan un método a un verbo HTTP y a una ruta.
  • "/eventos/{id}": las llaves marcan una parte variable de la ruta. Con GET /eventos/7, el id vale 7.
  • @PathVariable Long id: toma esa parte de la ruta y la entrega al método como parámetro.
Excepciones que aparecen: try, catch, DataAccessException, MailException
  • try { ... } catch (X e) { ... }: intenta el bloque; si ocurre un error de tipo X, salta al catch en lugar de romper el programa.
  • DataAccessException: error genérico de Spring cuando falla algo con la base de datos.
  • EntityNotFoundException: error propio de JPA cuando no se encontró el registro buscado.
  • MailException: error de Spring cuando el correo no pudo enviarse.

Los catch van de lo más específico a lo más general, y cada uno responde con su código.

¿Qué es @Slf4j y log.warn?

SLF4J es una fachada de logging: una forma estándar de escribir mensajes en la consola o en archivos. La anotación @Slf4j viene de Lombok y crea sola una variable log en la clase.

log.warn(...) escribe un mensaje de advertencia: algo salió mal pero el programa sigue. Los {} dentro del texto se reemplazan por los valores que siguen.
