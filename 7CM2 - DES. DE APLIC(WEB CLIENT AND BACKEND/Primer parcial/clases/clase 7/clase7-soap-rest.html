Por qué existe SOAP

Abre la Unidad II retomando la aplicación de propósito general que ya mencionó antes, y de ahí salta a la pregunta de fondo: cómo se comunican piezas hechas con tecnologías distintas.

"Formalmente dando carpetazo a la de inicio a la unidad dos. Que tiene que ver con servicios, APIs y demás. Entonces, como primera escala, vamos a platicar tantito de SOAP. Que es, literal, el protocolo simple de acceso a objetos."

La idea de partida: tengo un problema que resolver con varios tipos de software y varios lenguajes, así que necesito una forma de ponerlos a platicar. Si lo logro, ya no dependo de una base de datos, de un sistema operativo ni de un lenguaje en particular. Para lograrlo se apoya en protocolos estándar, es decir, reglas que todos aceptan.

¿Qué significa "sistemas heterogéneos"?

Sistemas hechos con tecnologías distintas: uno en Java, otro en .NET, otro en Python, con bases de datos y sistemas operativos diferentes. Lo contrario es un sistema homogéneo, donde todo usa la misma tecnología. Lo difícil de la integración es que cada pieza "habla" un formato distinto.

Aclaró que SOAP se enfoca sobre todo en el ámbito empresarial, porque cumple con los principios ACID del manejo de transacciones. Al recitarlos se trabó con el orden y él mismo se corrigió con un "bueno, en el orden correcto".

¿Cuáles son los principios ACID, en el orden correcto?
  • Atomicidad: la transacción se hace completa o no se hace.
  • Consistencia: la base pasa de un estado válido a otro válido.
  • Aislamiento: dos transacciones simultáneas no se estorban entre sí.
  • Durabilidad: lo confirmado no se pierde, aunque se caiga el sistema.

Él dijo "atomicidad, consistencia, durabilidad, aislamiento" y se corrigió; el orden de las siglas es el de arriba. Lo recordamos de cuando jugamos con bases de datos.

i

Precisión mía, no del profesor. Él dice que SOAP "le da cumplimiento" a ACID. Para el examen conviene decirlo así: SOAP se asocia con transacciones confiables. Ese soporte lo aportan las extensiones del estándar (la familia WS-*, como WS-AtomicTransaction), no el mensaje SOAP básico por sí solo.

Web Services: el intermediario entre lenguajes

Definió el servicio web y lo aterrizó con un sistema de facturación imaginario.

"Es aquel conjunto de normas, de reglas, de protocolos, de estándares, que nos van a poder permitir hacer que una aplicación escrita en .NET, por ejemplo, se comunique con una aplicación en Java, con una aplicación en Python o con cualquier cosa que se les ocurra."

El ejemplo fue el típico sistema de facturación con módulos en PHP, Java, .NET, Python y Go, que además corre en varias plataformas: Android, iPhone y HarmonyOS de Huawei, más web, escritorio y consola. Hay dos caminos para que se hablen: escribir tú un middleware, o usar servicios. Un servicio web hace el trabajo de un middleware.

¿Qué es un middleware?

Software que se coloca en medio de dos aplicaciones para traducir o coordinar lo que se dicen. Cada aplicación habla con el middleware en vez de hablar directo con la otra, y el middleware sabe cómo tratar con cada una.

El WSDL: el contrato

Para usar un servicio web hace falta un convenio entre las dos partes. Ese convenio es un documento XML.

"Necesitamos un convenio, de alguna manera, entre las dos partes. Y ese convenio no es otra cosa más que un documento basado en XML. [...] Se llama Web Service Descriptor Language, WSDL, que es el contrato."

La analogía fue la renta de un cuarto: quien ha rentado firmó un convenio con reglas (no llegar muy noche, no hacer escándalo, cuidar los espacios). Esas reglas son obligatorias para ambos. En un servicio web, el WSDL cumple ese papel: dice qué se debe seguir.

Concretamente, el WSDL dice:

  • cómo se llama el método;
  • qué tipo de dato espera recibir;
  • qué devuelve;
  • cómo se lo vamos a llamar.

Sirve para que las aplicaciones se pongan de acuerdo en el formato de recepción y de respuesta. Todo funciona por paso de mensajes, y lo que viaja es "una cadenota XML".

"¿Han hecho interfaces en Java? Y no interfaces gráficas de usuario, sino el public interface. El contrato, el que les dice el 'qué' se tiene que hacer. Bueno, pues es lo mismo."

¿Por qué compara el WSDL con un public interface?

Una interfaz de Java declara qué métodos existen, con qué parámetros y qué devuelven, pero no dice cómo se hacen. Quien la implementa decide el cómo. El WSDL hace lo mismo entre programas: fija el "qué" y deja libre el "cómo" a cada lado, sin importar en qué lenguaje esté hecho.

Al fondo de este bloque se le complicó cambiar de diapositiva con el proyector ("no quiere"). Fue una pausa breve, sin contenido.

Los cinco estándares que sostienen a SOAP

SOAP funciona porque se apoya en estándares que todos aceptan. Los fue nombrando uno por uno.

EstándarPara qué sirve, según él
HTTPEl protocolo de transferencia de hipertexto: "todos hemos agarrado el HTTP" para enviar datos y hacer peticiones.
SOAPEl protocolo del que trata la clase: define cómo se arma el mensaje.
WSDLEl descriptor: "dice qué podemos hacer con respecto al servicio web".
XMLEl formato en que se envían los datos que esperamos recibir.
XSDDefine los elementos que se esperan dentro del XML: qué tipo de dato es, si es obligatorio, si es lista, si tiene asociaciones. Son las reglas de validación del documento.

"Ustedes recordarán en sus clases que les dijeron que un XML tendría que ser bien formado y validado. La buena formación, pues, un montón de reglas que debe de cumplir. La validez, lo que le da el peso al documento, es cómo está conformado, la manera en que aparecen cada uno de los elementos."

¿Qué diferencia hay entre "bien formado" y "válido"?

Bien formado: cumple las reglas de sintaxis de XML. Todas las etiquetas cierran, hay un solo elemento raíz, los atributos van entre comillas. Cualquier lector de XML lo acepta.

Válido: además de estar bien formado, respeta las reglas de un esquema concreto (el XSD): que exista tal elemento, en tal orden, con tal tipo de dato. Un documento puede estar bien formado y no ser válido.

Al presentar el WSDL (bloque 3) el profesor pidió recordar la tercera y cuarta unidad de Tecnologías para el Desarrollo de Aplicaciones Web, donde se vio XML.

Lo que se logra con todo esto: sin importar en qué esté desarrollado tu proyecto, los distintos lenguajes van a poder intercambiar información. Bromeó con no saber si el proyector fallaba por el adaptador o por el cable; sin contenido técnico.

Bloque 6 · minuto ≈12:30 a 15:23

REST se apoya en HTTP

REST no inventa un protocolo nuevo. Aprovecha lo que ya trae HTTP.

Usa los verbos de HTTP para cada acción. Los que normalmente usamos: GET, POST, PUT, DELETE y PATCH. Sirven para recuperar uno o muchos, insertar, hacer actualizaciones totales o parciales, y borrar. Puede devolver los resultados en HTML, XML o lo que se te ocurra, pero lo típico es JSON.

"En el sentido estricto, cuando jugamos con REST, lo único que tenemos que hacer es seguir todo el conjunto de reglas que pudiera existir dentro del manejo del mismo protocolo. [...] Sabemos que el HTTP por definición es un protocolo sin estado, entonces a ustedes les toca encontrar la forma de garantizar la trazabilidad de las peticiones."

¿Qué quiere decir que HTTP no tiene estado?

Cada petición llega sola: el servidor no recuerda por sí mismo quién eres ni qué pediste antes. Si necesitas que una serie de peticiones se reconozcan como parte de lo mismo (una sesión, un carrito, un usuario ya autenticado), tienes que construir esa continuidad tú: con sesiones, cookies, tokens, etc. A eso se refiere con "trazabilidad".

También se siguen respetando los códigos de respuesta y de estado, "sobre todo para indicar si la petición fue satisfactoria, si es un recurso prohibido, si hay variedad de opciones y demás".

API, gateway y sistemas legados

Definió qué es una API, dibujó cómo se organiza y cerró con la pregunta de cuándo usar SOAP y cuándo REST.

"Por definición es una interfaz de programación de aplicaciones, y la regla es simple: es aquel conjunto de reglas, de normas, de protocolos que vamos a usar para poder integrar software de aplicaciones."

En la diapositiva aparecen dos piezas. El Backend System es lo que construimos del lado del servidor. El API Management System, o API Gateway, es el responsable de "determinar qué se puede hacer, quién puede responder y redireccionar al espacio correspondiente". Delante pueden estar aplicaciones de escritorio, web, móviles, de consola o dispositivos IoT, y todas se integran mientras exista manera de comunicarse. Ejemplo: sensores que disparan una acción y guardan datos; al usuario final solo le importa ver "numeritos" o una gráfica.

¿Qué hace un API Gateway?

Es la puerta de entrada única a tus servicios. Recibe todas las peticiones, decide si el solicitante puede hacerlas, y las manda al servicio interno correcto. Así los clientes no necesitan conocer la dirección de cada servicio.

La diferencia entre los dos

"Sistemas legados. Esas cosas raras que existen, que funcionan, sepa la... cómo. Donde ni siquiera hay documentación, o más bien la documentación pues ya se fue. ¿Y qué es más fácil? ¿Mantenerlos o actualizarlos? Típicamente trabajan con SOAP."

SOAPREST
Formato del mensajeXML, "sí o sí"JSON. También puede recibir y generar XML
Dónde lo verásSistemas legados; empresas muy formales; donde los esquemas de seguridad son un requisito de cumplimientoServicios web ligeros, Internet de las cosas, aplicaciones móviles, serverless
CarácterVerboso, con contrato (WSDL)Ligero, apoyado en los verbos de HTTP

Su conclusión práctica: cuando hagas cosas "muy empresariales, muy formales", lo más seguro es que tengas que lidiar con SOAP.

¿Qué es serverless?

Un modelo de nube donde subes funciones o pequeños servicios y el proveedor se encarga de los servidores: los levanta cuando llega una petición y cobra por uso. No significa que no haya servidores, sino que tú no los administras. El profesor solo lo listó como uno de los lugares donde REST es ideal.

Los verbos de REST y el nivel de madurez

Del lado de REST, lo primero es asociar cada verbo con las cuatro operaciones que de siempre hacemos: insertar, borrar, actualizar y seleccionar.

VerboOperaciónCuándo lo usó él
GETSeleccionarPara devolver uno o para devolver todos.
POSTInsertarCrear un recurso nuevo.
PUTActualizarSolo si la actualización es completa.
PATCHActualizarCuando la actualización es parcial: cambiar un solo atributo.
DELETEEliminarBorrar el recurso.

La razón de PATCH la explicó con un usuario recién creado:

"Se creó el usuario originalmente. Y hasta que no le pique a la liga que le llegó al correo electrónico, o al código que mandan, el OTP, hasta ese momento no se activa el usuario. Digamos que se crea pero en un estatus de falso. Para cambiar una variable en particular, un atributo, utilizamos PATCH."

Y si usas los cinco verbos, con versionado y documentación, ya le "estás pegando" a otro concepto: el nivel de madurez de Richardson para APIs. "Para empezar deberíamos cumplir los cinco, más otra cierta serie de características."

¿Qué es el modelo de madurez de Richardson?

Una escala que mide qué tan "REST de verdad" es una API, en cuatro niveles del 0 al 3. El profesor solo nombró el modelo; el resumen es mío:

  1. Nivel 0: un solo punto de entrada y HTTP usado solo como transporte.
  2. Nivel 1: aparecen los recursos, cada uno con su propia URL.
  3. Nivel 2: se usan bien los verbos HTTP y los códigos de estado.
  4. Nivel 3: la respuesta trae enlaces que dicen qué se puede hacer después (HATEOAS).

La estructura del mensaje es la misma que en SOAP, "solo que en lugar de apuntar al XML, apuntamos a un JSON. Y san se acabó". Y consumirlo es más transparente: para interactuar basta con apuntar al protocolo HTTP, no hace falta más. En Spring existe RestTemplate; en Java puro, o en cualquier lenguaje, basta con llamar a los métodos de HTTP.

Bloque 11 · minuto ≈29:43 a 31:26

Documentar una API: Swagger y RAML

Antes de construir, hay que poder decirle a otros qué hace tu API.

"La forma más rápida de documentar un API es agarrar Swagger. [...] Y si lo quieren hacer más detallado, más elaborado, o batallar tantito... pues siempre tenemos el RAML (RESTful API Modeling Language)."

Lo que busca es cumplir con estándares aceptados para generar la documentación, y Swagger lo hace. La pantalla que se ve enumera cada método y cómo interactuar con él. Ejemplos de lo que dijo que aparece:

  • GET /user para devolver a todos los usuarios;
  • GET /user/{id}, con un argumento que sirve de ID para la consulta;
  • para insertar, se pasa un objeto;
  • para actualizar, se pasa el objeto más el ID, "comúnmente".
¿Qué son Swagger y RAML, y en qué se parecen?

Las dos son formas de describir una API REST en un archivo estándar: qué rutas tiene, con qué verbos, qué parámetros recibe y qué devuelve. A partir de ese archivo se genera una página de documentación navegable (la de Swagger permite hasta probar cada método). Swagger es la más popular y la más rápida; RAML es más elaborada y orientada a modelar la API con detalle.

El primer controlador en Spring

Cierra asomándose a lo que se construye en la siguiente clase: un controlador REST en Java con Spring, y por qué no debe ser tan optimista.

Creas un controlador y lo decoras con @RestController, "porque es un API REST". Le pones un nombre para llegar a él con @RequestMapping. Luego defines un método por verbo, cada uno con su anotación: @PostMapping, @GetMapping, @PutMapping, @PatchMapping, "cada una de esas cosas". La del borrado no la nombró en voz alta, pero es @DeleteMapping.

Después no solo importa qué dato devuelves, sino qué código de respuesta le pintas al usuario. Para eso está @ResponseStatus con un HttpStatus:

Si el método…El HttpStatus es
borraNO_CONTENT
creaCREATED
actualizaOK
consultaOK

"¿Qué otra cosa? Nada más. Con esos tenemos."

El problema: es muy "happy path"

Así como está, el controlador asume que todo siempre sale bien: se ejecuta, hace todo, devuelve y listo. No se valida nada. Pero rara vez ocurre así, y los códigos de respuesta los va a controlar el alumno. El ejemplo que dio, con la carrera:

"Voy a dar de alta una carrera para ESCOM, y la carrera que voy a dar de alta es ISC. El mismo nombre ya está registrado. Entonces no me debería de permitirlo. Por lo tanto, debería de botarme alguna excepción."

Otros casos que nombró: no se logró conectar a la base de datos, ocurrió un error interno del servidor, no se encontró el recurso, o el recurso no está permitido para ese usuario con esos privilegios. "Todo eso los tenemos que manejar nosotros."

¿Qué es un "happy path"?

El camino en el que todo sale bien: los datos llegan correctos, la base responde, el usuario tiene permiso. El código de "happy path" solo cubre ese camino. El código de verdad tiene que prever los errores: datos duplicados, fallos de conexión, recursos que no existen.

Por eso las firmas simples como public Evento read() o public Evento save(@RequestBody Evento e) no deberían quedar así. @RequestBody hace el mapeo del JSON recibido a la clase, pero lo que se devuelve no debería ser la entidad sola:

"Lo que deberíamos de devolver no es la entidad en sí. Tendríamos que devolver un ResponseEntity. Para poder interactuar con él, y a lo mejor poder determinar si se puede o si no se puede hacer tal o cual cosa."
