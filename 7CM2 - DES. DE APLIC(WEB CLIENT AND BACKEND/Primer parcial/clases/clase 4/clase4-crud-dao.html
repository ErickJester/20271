¿Por qué la clase se llama CarreraDAO y no nada más Carrera?

Son dos clases con trabajos distintos, y por eso son dos archivos distintos:

  • Carrera es el dato. Solo guarda un id, un nombre y una descripción. No sabe que existe una base de datos.
  • CarreraDAO es el que habla con la base de datos. Sabe conectarse, sabe SQL, y sabe convertir filas de tabla en objetos Carrera y al revés.

Esa separación es todo el patrón DAO (Data Access Object): si mañana cambias de MySQL a PostgreSQL, tocas CarreraDAO y nada más. La clase Carrera ni se entera, y el resto de tu aplicación tampoco.

El sufijo DAO en el nombre es puro convenio para que se lea de inmediato qué hace. Las cinco constantes SQL

Antes de cualquier método, arriba de la clase van las consultas guardadas como constantes. Una por operación del CRUD.

La forma es siempre la misma y la escribió cinco veces:

// las cinco, arriba de todo, dentro de la clase CarreraDAO
private static final String SQL_INSERT =
    "INSERT INTO Carrera (nombreCarrera, descripcionCarrera) VALUES (?, ?)";

private static final String SQL_UPDATE =
    "UPDATE Carrera SET nombreCarrera = ?, descripcionCarrera = ? WHERE idCarrera = ?";

private static final String SQL_DELETE =
    "DELETE FROM Carrera WHERE idCarrera = ?";

private static final String SQL_SELECT =
    "SELECT * FROM Carrera WHERE idCarrera = ?";

private static final String SQL_SELECT_ALL =
    "SELECT * FROM Carrera";
Desármame private static final String, palabra por palabra

Son cuatro cosas apiladas y cada una dice algo distinto:

  • private — solo el código dentro de CarreraDAO puede verla. Nadie de fuera necesita saber qué SQL usas.
  • static — existe una sola copia, compartida por toda la clase, no una por cada objeto. Si creas cien CarreraDAO, el texto del INSERT sigue estando una sola vez en memoria. Tiene sentido porque la consulta nunca cambia entre un objeto y otro.
  • final — una vez asignada, no se puede reasignar. Intentar SQL_INSERT = "otra cosa" más adelante no compila.
  • String — el tipo. Es texto, nada más. Java no sabe ni le importa que ese texto sea SQL; para él es una cadena cualquiera.

Y sobre el nombre en MAYÚSCULAS con guiones bajos: eso no es obligación del compilador, es convención. Él lo dijo así: "eso más que el nombre del atributo que esté en mayúsculas, se entiende que es una constante". En Java no existe la palabra const — está reservada pero no se puede usar. private static final más el nombre en mayúsculas es lo más cercano que hay.

¿Qué hacen los signos ? ahí sueltos?

Son huecos. La consulta queda escrita completa salvo por los valores, que se rellenan justo antes de ejecutarla.

Esto es lo que hace un PreparedStatement: manda la consulta al motor de base de datos con los huecos vacíos, el motor la analiza y la deja lista, y hasta después le pasas los valores por separado. Como el motor ya decidió qué es estructura y qué es dato, un valor malicioso no puede convertirse en instrucción.

Ese es el motivo real de que en la clase 3 dijera que nunca usen Statement: con Statement concatenas el valor dentro del texto SQL, y ahí es donde vive la inyección SQL.

// NO. Esto es concatenar: el valor entra al texto de la consulta.
"SELECT * FROM Carrera WHERE idCarrera = " + id

// SÍ. El hueco viaja aparte del valor.
"SELECT * FROM Carrera WHERE idCarrera = ?"

Sobre escribirlas en una sola línea. Insistió en eso: "todo eso en una línea, porque si está en múltiples líneas, pues no se les olvide cerrar por acá, concatenar y demás cosas". Java no tiene cadenas de varias líneas en la sintaxis clásica: si partes el texto, tienes que cerrar comillas, poner +, abrir comillas otra vez, y acordarte del espacio. Ese espacio olvidado es el bug clásico:

// se convierte en "...FROM CarreraWHERE idCarrera = ?"  ->  error de sintaxis SQL
"SELECT * FROM Carrera" +
"WHERE idCarrera = ?"

También mencionó que si necesitas más consultas —"hacer joins, inner joins, lo que se les ocurra, left, outer"— aquí es donde van: una constante más y un método más. El DAO crece por ahí, no por otro lado.

La pista ya salió en clase. Un alumno preguntó "¿tiene que ver con los grados de borrado, borrado suave y borrado duro?" y él confirmó: "sí, justo. O borrado lógico, borrado físico".

Adelanto: la idea del borrado lógico en una línea

En vez de sacar la fila de la tabla, le pones una marca de que ya no está vigente. Una columna extra, típicamente activo BOOLEAN o fechaBaja DATETIME.

El DELETE deja de ser un DELETE y se convierte en un UPDATE:

-- borrado físico: la fila desaparece
DELETE FROM Carrera WHERE idCarrera = ?;

-- borrado lógico: la fila sigue ahí, marcada
UPDATE Carrera SET activo = false WHERE idCarrera = ?;

El costo es que todas tus consultas de lectura tienen que empezar a filtrar (WHERE activo = true), y si se te olvida en una, aparecen registros fantasma. Ese trade-off es justo lo que la investigación tiene que discutir: no te quedes en la definición.

Un cabo que amarra con la clase 3: en el DTO de inserción, activo normalmente no va, porque la base de datos ya le pone su valor por defecto.

create() y la anatomía de un método DAO

El primer método completo. Todos los demás son variaciones de esta misma plantilla, así que aquí es donde conviene entender de verdad.

Antes de los métodos hay que declarar un atributo de la clase que guarde la conexión viva. Él lo puso a media pizarra buscando espacio: Connection conexion;. Con eso, el método queda:

public void create(Carrera c) throws SQLException {

    obtenerConexion();                    // 1. llena el atributo conexion
    PreparedStatement ps = null;          // 2. lo declara vacío

    try {
        ps = conexion.prepareStatement(SQL_INSERT);   // 3. prepara la consulta
        ps.setString(1, c.getNombreCarrera());        // 4. llena el hueco 1
        ps.setString(2, c.getDescripcionCarrera());   //    y el hueco 2
        ps.executeUpdate();                           // 5. la ejecuta
    } finally {
        if (ps != null) ps.close();                   // 6. cierra, pase lo que pase
        if (conexion != null) conexion.close();
    }
}

Seis pasos. Los cinco métodos del CRUD son este mismo esqueleto cambiando la constante, los set y la forma de ejecutar. Vamos uno por uno.

Pasos 1 y 2 · La conexión y el PreparedStatement

La primera línea del método llama al método de conexión que escribieron la clase pasada. Ni él se acordaba del nombre exacto: "si el método que escribimos en esa ocasión se llama conéctate(), pues conéctate()". Ahí adentro está el DriverManager.getConnection() cuyo resultado se guarda en el atributo conexion.

¿Qué es exactamente un PreparedStatement?

Es el objeto de Java que representa una consulta lista para ejecutarse contra una conexión concreta.

La conexión sola no ejecuta nada: es apenas el cable hacia la base. El PreparedStatement es lo que viaja por ese cable. El flujo completo es:

  1. Le pides a la conexión que prepare un texto SQL: conexion.prepareStatement(SQL_INSERT).
  2. Te devuelve un objeto PreparedStatement. La base ya analizó la consulta y sabe qué va a hacer.
  3. Le pasas los valores de los huecos con setString, setInt, etcétera.
  4. Le dices que se ejecute.

Se declara en null afuera del try a propósito. Si lo declararas adentro, el finally no podría verlo para cerrarlo: una variable solo vive dentro de las llaves donde se declaró.

Los tres verbos que usó para describir prepareStatement son buenos: "¿qué consulta va a parametrizar, va a programar, va a planificar?".

Paso 4 · Los índices empiezan en 1

Aquí está la parte que más se equivoca. Numeró los ? en el pizarrón y luego numeró los set:

"La lista de argumentos empieza en 1 y termina en N."

No en cero. Es una de las poquísimas cosas en Java que no arranca en cero, y es precisamente porque ese índice no es de Java: es del SQL. La firma completa es ps.setString(índice, valor): primero cuál hueco, después qué le metes.

¿Y de dónde sale el valor? Del objeto Carrera que llegó como argumento. Preguntó en clase quién conoce el nombre de la carrera, y la respuesta es el propio objeto: c.getNombreCarrera(). Eso implica que alguien tuvo que llenar ese objeto antes, en otro lado:

c.setNombreCarrera("ISC");
c.setDescripcionCarrera("La carrera de ISC");

// ahora c "conoce" esos datos, y es lo que se le pasa al DAO
dao.create(c);

Paso 5 · Solo hay dos formas de ejecutar

Preguntó qué tipos de consulta SQL les enseñaron en Bases de Datos, y fueron saliendo: inserción, actualización, eliminación, selección. Cuatro. Y entonces vino el remate:

"En teoría les presentaron al menos cuatro. Para nosotros solo hay dos: ps.executeUpdate() y san se acabó."

Es la simplificación más útil de toda la clase. Desde JDBC, las cuatro familias de SQL colapsan en dos métodos según qué te devuelven:

MétodoPara qué SQLQué devuelve
executeUpdate()INSERT, UPDATE, DELETE — todo lo que modifica filasun int: cuántas filas cambió
executeQuery()SELECT, con o sin joinsun ResultSet: las filas encontradas

El nombre executeUpdate confunde porque suena a que solo sirve para UPDATE. No: sirve para las tres que modifican. Piénsalo como "ejecutar una actualización de la tabla", no "ejecutar un UPDATE".

Paso 6 · finally, no catch

Aquí hizo algo que parece descuido y es decisión:

"Como todo bloque try, si intenta hacer algo y si no puedes lanza la excepción, debiera de haber un catch. No le vamos a poner catch, le vamos a poner un finally."

try / catch / finally: qué hace cada uno
  • try — "intenta esto". Si algo truena adentro, el resto del bloque se salta.
  • catch — "si tronó, haz esto en su lugar". Atrapa el error y lo detiene ahí.
  • finally — "esto se ejecuta pase lo que pase". Salga bien, truene, o incluso si hay un return en medio.

Su formulación: "el 'intenta', si no puedes lanza el error, y el otro es 'no me interesa si pudiste o no pudiste, esto se ejecuta'".

Poner finally sin catch es legal, y es exactamente lo que quieres aquí: no vas a resolver el error (no es tu trabajo), pero sí tienes que cerrar la conexión antes de irte. Si pusieras un catch, te tragarías el error y quien llamó al método creería que todo salió bien.

Y adentro del finally, las dos preguntas. Primero el statement, después la conexión:

} finally {
    if (ps != null) ps.close();
    if (conexion != null) conexion.close();
}
¿Por qué el if (ps != null)? ¿Y por qué en ese orden?

El if: el finally se ejecuta siempre, incluso si la conexión falló y ps se quedó en null. Llamar .close() sobre null revienta con un NullPointerException, y lo peor es que ese error nuevo tapa el error original que sí querías ver.

El orden: al revés de como se abrieron. Primero se abrió la conexión, luego el statement; se cierran statement primero, conexión al último. El statement depende de la conexión, así que cerrar la conexión antes lo dejaría colgado.

Cerrar importa de verdad: cada conexión abierta ocupa un recurso del servidor de base de datos, y hay un límite. Un método que se olvida de cerrar cuando hay error va agotando el pozo hasta que la aplicación entera deja de poder conectarse. Eso se llama fuga de conexiones y es de los bugs más difíciles de rastrear, porque tarda horas en manifestarse.

Las excepciones son una carrera de relevos

Si el método no atrapa el error, ¿quién lo atrapa? Esta fue la mejor analogía de la clase.

"¿Qué pasa con los errores? 'Ah, bueno, es que no pude insertar'. Se lanza una excepción. ¿Quién le va a dar tratamiento? La capa de arriba. Imagínense que están jugando carreras de relevos. ¿Aquí le tiran la estafeta a quién? Pues al que sigue."

El throws SQLException en la firma del método es precisamente eso: el aviso de que este método no resuelve el problema, solo lo pasa. Y quién es "el que sigue" depende del tipo de aplicación:

Tipo de aplicaciónQuién recibe la estafeta
EscritorioLa capa que genera la interfaz gráfica: Swing, JavaFX
WebEl Servlet, el JSP — y en el stack del curso, el controlador de Spring
MóvilLa capa que comunica y pinta el error al cliente
¿Qué es una "excepción" y qué significa throws en la firma?

Ya lo había dicho en la clase 3: en Java no hay errores, hay excepciones. Una excepción es un objeto que representa "algo salió mal", que interrumpe el flujo normal y va subiendo por la cadena de quién llamó a quién hasta que alguien la atrape.

SQLException es una excepción checked: el compilador te obliga a hacer algo con ella. Solo tienes dos opciones y no hay tercera:

  • Atraparla aquí mismo con try/catch.
  • Declararla con throws SQLException en la firma, que es decir "yo no, que la atrape el que me llamó".

El DAO elige la segunda. Por eso, en cuanto escribas dao.create(c) en otro lado, el compilador te va a marcar error hasta que ahí pongas el try/catch. Él lo describió como si el compilador te reclamara: "oye, espérate, el método que tú pretendes ejecutar dice que probablemente genere una excepción. No lo estás tratando allá, lo tengo que tratar yo".

Y cuando por fin la atrapas, no pongas printStackTrace

En el main, el catch más directo sería catch (SQLException e), o el genérico catch (Exception e). Y adentro, lo que todo mundo escribe: e.printStackTrace(). Sobre eso fue tajante:

"La realidad dicta que el printStackTrace() no lo pongan. Ahí tendrían que poner un log en SLF4J, que es un Simple Logging Facade for Java. O el manejador de logs específico, para que eso lo mande al server y no sea tan escandaloso para el usuario."

Stack trace, log y SLF4J: qué es cada cosa

Un stack trace es la lista de métodos que estaban en curso cuando reventó, del más profundo al más superficial. Es utilísimo para depurar y es exactamente lo que no quieres que vea un usuario final: le enseña nombres de tus clases, rutas de archivos y a veces datos.

printStackTrace() lo escupe en la consola. Problemas: en un servidor no hay una consola que alguien esté mirando, no queda registrado en ningún lado con fecha, y no puedes apagarlo ni filtrarlo.

Un log es un registro con fecha, nivel de severidad (ERROR, WARN, INFO, DEBUG) y destino configurable: archivo, servidor central, lo que sea. Puedes decir "en producción solo quiero ERROR" sin tocar el código.

SLF4J (Simple Logging Facade for Java) es una fachada: una capa intermedia con la que tu código habla, para que la librería de logging real (Logback, Log4j) se pueda cambiar sin tocar tus clases. Es el mismo razonamiento del patrón DAO: hablar con una abstracción, no con la implementación.

Y el detalle que agregó al final: printStackTrace() no es lo único que trae la excepción; también está e.getMessage(), que da el mensaje específico del error y suele ser lo que sí quieres mostrar o registrar.

update()

"Necesito colorcitos." A partir de aquí cambió de marcador por cada método, y por eso esta página está dividida así.

Su descripción fue literalmente "lo mismo": obtiene la conexión, genera un PreparedStatement, recibe una Carrera. Solo cambian tres cosas.

public void update(Carrera c) throws SQLException {

    obtenerConexion();
    PreparedStatement ps = null;

    try {
        ps = conexion.prepareStatement(SQL_UPDATE);       // cambio 1: la constante
        ps.setString(1, c.getNombreCarrera());
        ps.setString(2, c.getDescripcionCarrera());
        ps.setInt(3, c.getIdCarrera());                    // cambio 2: un tercer parámetro
        ps.executeUpdate();
    } finally {
        if (ps != null) ps.close();
        if (conexion != null) conexion.close();
    }
}

El tercer parámetro es el que trae la novedad, y trae las dos cosas juntas: índice 3 porque es el tercer ? de la consulta, y setInt porque idCarrera es un entero, no texto. Los dos primeros son copiar y pegar del create.

La pregunta que salió: ¿dónde se manda el nombre nuevo?

Un alumno preguntó algo que suena básico y no lo es: "¿en qué parte le mandamos, por ejemplo, el nuevo nombre?". Es la confusión natural, porque en el método no aparece por ningún lado un "nombre nuevo".

La respuesta es que el método no distingue entre viejo y nuevo. El objeto Carrera que le llega ya trae los valores que van a quedar. Quien lo llama es el que decide:

Carrera c1 = new Carrera();
c1.setIdCarrera(1);                                   // A CUÁL registro le pega
c1.setNombreCarrera("LCD");                           // los valores NUEVOS
c1.setDescripcionCarrera("La carrera de LCD");

dao.update(c1);

Ese objeto lleva dos cosas de naturaleza distinta y conviene no revolverlas: el id dice a cuál fila pegarle, y los otros dos campos dicen con qué valores dejarla.

Ojo con esto: es una actualización completa

Él lo dijo de pasada y es importante: "ya tenemos un método que permite actualizar valores, pero hace una actualización completa".

El SET reescribe las dos columnas siempre. Si solo querías cambiar la descripción y mandas el objeto con nombreCarrera en null, no es que el nombre se quede como estaba: se borra y queda en null.

Por eso el flujo correcto es: primero lee el registro completo con read(), luego cambias en el objeto solo lo que quieres cambiar, y ese objeto completo se lo mandas al update(). Es exactamente la razón por la que en el bloque siguiente insiste en que actualizar incluye buscar.

delete()

El más corto de los cinco, y donde se ve mejor que el índice del parámetro no se hereda: se recalcula por consulta.

Borró del pizarrón las dos primeras líneas del update porque el DELETE solo necesita el id, y luego reescribió la tercera. Ese fue el punto:

"El único detalle: el índice no es el 3, el índice es único, entonces sería 1."

public void delete(Carrera c) throws SQLException {

    obtenerConexion();
    PreparedStatement ps = null;

    try {
        ps = conexion.prepareStatement(SQL_DELETE);
        ps.setInt(1, c.getIdCarrera());     // 1, no 3: en ESTA consulta es el único ?
        ps.executeUpdate();                    // DELETE también es executeUpdate
    } finally {
        if (ps != null) ps.close();
        if (conexion != null) conexion.close();
    }
}

El índice cuenta los huecos de la consulta que estás ejecutando, no la posición del atributo en la clase ni el orden de las columnas en la tabla. En SQL_UPDATE el id es el tercer ?; en SQL_DELETE es el único, así que es el 1.

Caso de uso y <<include>>, explicados desde cero

Un caso de uso es una cosa que un usuario quiere lograr con el sistema, escrita en verbo: "Actualizar carrera", "Registrar alumno". En UML se dibuja como un óvalo.

<<include>> es una relación entre dos casos de uso que significa "este otro siempre pasa como parte de este". No es opcional, no es un caso especial: siempre ocurre.

Aquí: Actualizar carrera <<include>> Buscar carrera. No hay forma de actualizar sin buscar primero, así que la relación es de inclusión y no una alternativa.

public static void main(String[] args): qué significa cada palabra

Es la puerta de entrada: cuando corres el programa, Java busca exactamente este método y empieza ahí.

  • public — Java tiene que poder llamarlo desde fuera de tu clase.
  • static — se ejecuta sin necesidad de crear un objeto de la clase. Tiene que ser así, porque al arrancar todavía no existe ningún objeto.
  • void — no devuelve nada.
  • main — el nombre es obligatorio, Java busca ese exacto.
  • String[] args — los argumentos que le pasarías desde la línea de comandos. Casi nunca se usan, pero la firma los pide.

Un paquete es una carpeta con nombre largo que agrupa clases. com.ipn.mx.modelo es una carpeta real: com/ipn/mx/modelo/.

Fíjate en los nombres que usó, porque describen la separación de responsabilidades: .modelo para las clases de datos, .dao para las de acceso a base. Esa convención la vas a volver a ver en Spring, con .controlador, .servicio y .repositorio.

readAll() y el método que arma la lista

Aquí sí cambia la plantilla. Los tres anteriores no devolvían nada; este devuelve datos, y eso obliga a dos piezas nuevas: un ResultSet y un método auxiliar.

public List readAll() throws SQLException {

    obtenerConexion();
    PreparedStatement ps = null;
    ResultSet rs = null;              // pieza nueva 1
    List resultados = null;

    try {
        ps = conexion.prepareStatement(SQL_SELECT_ALL);
        // esta consulta NO tiene ?, así que no hay ningún ps.set...
        rs = ps.executeQuery();           // executeQuery, porque es SELECT

        resultados = obtenerResultados(rs);  // pieza nueva 2

        if (resultados.size() > 0) {
            return resultados;
        } else {
            return null;
        }
    } finally {
        if (rs != null) rs.close();          // ahora son TRES cierres
        if (ps != null) ps.close();
        if (conexion != null) conexion.close();
    }
}

Tres detalles que cambian respecto a los métodos anteriores:

  • No recibe argumentos. Su explicación: "¿qué argumentos necesita? Ninguno. Porque la consulta es un SELECT * FROM lo que sea, punto. No hay parámetros". Cero ?, cero set.
  • Devuelve una lista. Sobre el tipo dijo "ustedes determinen si es una lista tipada o no" y la dejó genérica. En tu código conviene List<Carrera>, que es la versión tipada.
  • Ahora se cierran tres cosas, y en orden inverso al de apertura: rs, ps, conexion.
¿Qué es un ResultSet?

Es lo que devuelve un SELECT: las filas que encontró. Pero no es una lista y ahí está la trampa.

Un ResultSet es un cursor: un dedo apuntando a una fila a la vez, que solo sabe avanzar. Arranca antes de la primera fila, y cada rs.next() lo mueve una posición y devuelve true si cayó en una fila real, o false si ya se acabaron. Por eso el recorrido siempre se escribe igual:

while (rs.next()) {
    // aquí rs apunta a UNA fila; se leen sus columnas
}

Y por eso hay que convertirlo a una lista de objetos: el ResultSet deja de servir en cuanto cierras la conexión. Si lo devolvieras tal cual desde el DAO, quien lo recibe tendría un objeto muerto. La lista de Carrera sí sobrevive porque son objetos de Java normales.

Y de paso, devolver un ResultSet rompería el patrón DAO: el resto de la aplicación se enteraría de que existe JDBC.

¿Por qué List y qué es List<Carrera>?

List es una colección ordenada que crece sola, a diferencia de un arreglo, que nace con tamaño fijo. Como no sabes cuántas carreras hay en la tabla, un arreglo no sirve.

List es una interfaz (dice qué se puede hacer) y ArrayList es la implementación (dice cómo). Por eso se escribe List r = new ArrayList();: declaras por la interfaz, instancias con la implementación. Así puedes cambiar a otra implementación después tocando una sola línea.

Los <Carrera> son genéricos: le dicen al compilador que ahí solo caben objetos Carrera. Sin ellos, la lista acepta cualquier cosa y al sacar elementos tienes que hacer cast a mano, con riesgo de reventar en tiempo de ejecución. Con genéricos, el error salta al compilar.

List sin = new ArrayList();                   // cabe lo que sea
Carrera c = (Carrera) sin.get(0);             // cast obligatorio, puede tronar

List<Carrera> con = new ArrayList<>();        // solo Carreras
Carrera c2 = con.get(0);                      // sin cast, seguro

Él cerró diciendo "ustedes lo pueden hacer con lo que quieran: tienen Set, Vector, Collection, lo que se les ocurra". Cierto, pero para esto List es la correcta: mantiene el orden y admite repetidos.

obtenerResultados(): donde las filas se vuelven objetos

Cuando llegó a la línea de obtenerResultados(rs) hizo algo que vale la pena copiarle como técnica:

"¿Qué hace obtenerResultados()? No sé. En este punto no me interesa, solo sé que me regresa una lista y se la asigna a resultados."

Escribió el método de arriba como si el de abajo ya existiera, y hasta después lo escribió. Es la forma sana de atacar un problema: resuelves un nivel a la vez y confías en que el de abajo cumplirá su contrato.

private List obtenerResultados(ResultSet rs) throws SQLException {

    List r = new ArrayList();

    while (rs.next()) {                                          // mientras haya filas
        Carrera c = new Carrera();                               // una instancia POR fila
        c.setIdCarrera(rs.getInt("idCarrera"));                  // getInt: es entero
        c.setNombreCarrera(rs.getString("nombreCarrera"));       // getString: es VARCHAR
        c.setDescripcionCarrera(rs.getString("descripcionCarrera"));
        r.add(c);                                                // se agrega a la lista
    }
    return r;
}

Es privado porque nadie fuera del DAO lo necesita: es plomería interna. Y fíjate en la simetría con lo que ya sabes: al escribir usabas ps.setString(1, valor) con índice numérico; al leer usas rs.getString("nombreCarrera") con el nombre de la columna entre comillas. Mismos tipos, misma lógica, dirección contraria.

Cuidado: ese nombre entre comillas es de la tabla, no de Java

rs.getString("nombreCarrera") le pregunta a la fila por su columna llamada nombreCarrera. Ese texto tiene que coincidir con el nombre de la columna en la base de datos, no con el nombre del atributo en tu clase.

Aquí coinciden porque las nombraron igual a propósito. El día que la columna se llame nombre_carrera y el atributo nombreCarrera, el que manda es el de la base.

Y como es un texto entre comillas, el compilador no lo revisa: si te equivocas de nombre, Java compila feliz y truena en tiempo de ejecución con un SQLException diciendo que esa columna no existe. Es de los errores más comunes en JDBC.

    PreparedStatement ps = null;
    ResultSet rs = null;
    List resultados = null;

    try {
        ps = conexion.prepareStatement(SQL_SELECT);   // el que lleva WHERE
        ps.setInt(1, c.getIdCarrera());                // este SÍ tiene un ?
        rs = ps.executeQuery();

        if (resultados.size() > 0) {
            return (Carrera) resultados.get(0);          // la primera coincidencia
        } else {
            return null;
        }

        if (ps != null) ps.close();
        if (conexion != null) conexion.close();
    }
}

Reusa obtenerResultados() tal cual, y el truco está en la última parte: como la consulta filtra por clave primaria, la lista va a traer un solo elemento. resultados.get(0) lo saca. En este método aparecen un 1 y un 0 muy juntos y significan cosas distintas:

  • resultados.get(0) — el primer elemento de una lista de Java. Las colecciones de Java empiezan en 0.

Regla para no dudar: si el número se lo estás dando a SQL, empieza en 1. Si se lo estás dando a Java, empieza en 0.

Stored procedures: la misma inserción, del lado de la base

"¿A quién le gusta ser DBA aquí? A ninguno de ustedes les gustan las bases de datos, ¿no? ¡Qué bárbaro!" Y con eso arrancó la última parte, que existe para preparar el ejercicio 2.

¿Qué es un stored procedure? ¿Y un DBA?

Un stored procedure (procedimiento almacenado) es código SQL con nombre que vive guardado dentro de la base de datos, no en tu aplicación. Lo escribes una vez, se queda ahí, y desde Java solo lo mandas llamar por su nombre.

Es como un método, pero del lado de la base: recibe parámetros, ejecuta instrucciones y puede devolver resultados.

Ventajas: la lógica queda en un solo lugar aunque la usen varias aplicaciones, viaja menos texto por la red, y la base puede tenerlo pre-optimizado. Desventajas: queda amarrado a ese manejador, es más difícil de versionar en Git, y te reparte la lógica de negocio entre dos lugares.

Un DBA (Database Administrator) es la persona encargada de la base de datos: diseño, respaldos, permisos, rendimiento. Los stored procedures suelen ser su territorio, y por eso preguntó a quién le gustaba serlo.

La advertencia antes de escribirlo, que es la que va al examen:

"Aquí es literal: depende del manejador de datos. No es lo mismo esto que vamos a apuntar que va a funcionar en un MySQL que si se lo quieren llevar a un PostgreSQL, a un Oracle o lo que sea. Ahí el ANSI SQL dejó de ser tú."

¿Qué es "ANSI SQL" y por qué "dejó de ser tú"?

ANSI SQL es el SQL estándar, el que todos los manejadores acordaron soportar igual. Los SELECT, INSERT, UPDATE y DELETE básicos que llevas escribiendo toda la clase son ANSI: los mueves de MySQL a PostgreSQL y funcionan sin tocarlos.

Los procedimientos y funciones no. Cada manejador se inventó su propio lenguaje: Oracle usa PL/SQL, SQL Server usa T-SQL, PostgreSQL usa PL/pgSQL, MySQL el suyo. Cambia la sintaxis para declarar parámetros, para el cuerpo, y hasta la palabra para invocarlo.

La consecuencia práctica: en cuanto usas stored procedures, cambiar de base de datos deja de ser gratis. Y eso choca de frente con la razón de existir del patrón DAO, que era justamente aislar ese cambio.

DELIMITER //

CREATE PROCEDURE sp_crear(nombre VARCHAR(50), descripcion VARCHAR(100))
BEGIN
    INSERT INTO Carrera (nombreCarrera, descripcionCarrera)
    VALUES (nombre, descripcion);
END //

DELIMITER ;

Fíjate en que adentro no hay ni un ?. Los huecos se volvieron parámetros con nombre (nombre, descripcion) y se usan directo. Los tipos y tamaños los sacó de cómo esté definida la tabla —"no me acuerdo qué tamaños tenía esa cosa, depende de cómo esté definido en bases de datos"—, así que revisa los tuyos.

El DELIMITER: por qué sin él "les va a decir de groserías"

Normalmente el punto y coma le dice a MySQL "aquí termina la instrucción, ejecútala".

El problema es que el cuerpo del procedimiento tiene punto y comas adentro (los del INSERT). Sin protección, MySQL lee hasta el primer ;, cree que ahí terminó el CREATE PROCEDURE, e intenta ejecutar algo incompleto. De ahí el error.

DELIMITER // cambia temporalmente el terminador a //. Ahora los ; de adentro son texto normal, y el procedimiento termina cuando aparece //. Al final, DELIMITER ; lo regresa a la normalidad para que el resto de tu sesión siga funcionando.

Ese último DELIMITER ; se olvida muchísimo, y el síntoma es raro: todo lo que escribas después parece no ejecutarse.

Y una cosa que dejó abierta: "aquí pueden poner todas las condicionales que quieran, todo el manejo de error que quieran propio del SQL para determinar que lo que están recibiendo realmente sea una cadena de texto válida. Pero eso ya les toca a ustedes".

Ejercicio 2 — Cambiar PreparedStatement por CallableStatement

"Esto lo tienen con PreparedStatement, cámbienlo con CallableStatement. Según su lectura rápida JDBC, el otro es este cuate: el CallableStatement. ¿Para cuándo? Para la próxima semana."

Es la única tarea con fecha explícita. Las otras tres no la llevan; esta sí.

Qué implica. Los cinco métodos del DAO se quedan igual en estructura. Lo que cambia es que en vez de preparar SQL suelto, mandas llamar procedimientos almacenados. O sea que primero tienes que crear los procedimientos en MySQL: él solo escribió el de insertar, los otros cuatro te tocan.

La forma general del cambio, para que veas que es menos de lo que parece:

// antes
PreparedStatement ps = conexion.prepareStatement(SQL_INSERT);

// después
CallableStatement cs = conexion.prepareCall("{call sp_crear(?, ?)}");

Los ? siguen ahí y los setString / setInt se usan igual, con la misma numeración desde 1. Cuando señaló qué se iba a cambiar dijo "ah, pues sí, sí, sí, ese, ese, ese" apuntando a esas líneas: es un reemplazo bastante mecánico.

Y la razón de que la Tarea 2 importe: CallableStatement tiene una capacidad que los otros no —los parámetros de salida (OUT)— y eso viene explicado en la lectura rápida de JDBC. Ahí es donde deja de ser mecánico.

El DAO completo, de corrido

Todo lo del pizarrón junto y en orden, ya con los imports que hacen falta y con la lista tipada. Esta es la versión contra la que puedes comparar tu archivo.

CarreraDAO.java
import java.sql.Connection;
import java.sql.DriverManager;
import java.sql.PreparedStatement;
import java.sql.ResultSet;
import java.sql.SQLException;
import java.util.ArrayList;
import java.util.List;

public class CarreraDAO {

    private static final String SQL_INSERT =
        "INSERT INTO Carrera (nombreCarrera, descripcionCarrera) VALUES (?, ?)";
    private static final String SQL_UPDATE =
        "UPDATE Carrera SET nombreCarrera = ?, descripcionCarrera = ? WHERE idCarrera = ?";
    private static final String SQL_DELETE =
        "DELETE FROM Carrera WHERE idCarrera = ?";
    private static final String SQL_SELECT =
        "SELECT * FROM Carrera WHERE idCarrera = ?";
    private static final String SQL_SELECT_ALL =
        "SELECT * FROM Carrera";

    private Connection conexion;

    private void obtenerConexion() throws SQLException, ClassNotFoundException {
        String usuario = "root";
        String clave = "tu_password";
        String urlBD = "jdbc:mysql://localhost:3306/MisCursos";
        String driverMySQL = "com.mysql.cj.jdbc.Driver";

        Class.forName(driverMySQL);
        conexion = DriverManager.getConnection(urlBD, usuario, clave);
    }

    // ---------- create ----------
    public void create(Carrera c) throws SQLException {
        obtenerConexion();
        PreparedStatement ps = null;
        try {
            ps = conexion.prepareStatement(SQL_INSERT);
            ps.setString(1, c.getNombreCarrera());
            ps.setString(2, c.getDescripcionCarrera());
            ps.executeUpdate();
        } finally {
            if (ps != null) ps.close();
            if (conexion != null) conexion.close();
        }
    }

    // ---------- update ----------
    public void update(Carrera c) throws SQLException {
        obtenerConexion();
        PreparedStatement ps = null;
        try {
            ps = conexion.prepareStatement(SQL_UPDATE);
            ps.setString(1, c.getNombreCarrera());
            ps.setString(2, c.getDescripcionCarrera());
            ps.setInt(3, c.getIdCarrera());
            ps.executeUpdate();
        } finally {
            if (ps != null) ps.close();
            if (conexion != null) conexion.close();
        }
    }

    // ---------- delete ----------
    public void delete(Carrera c) throws SQLException {
        obtenerConexion();
        PreparedStatement ps = null;
        try {
            ps = conexion.prepareStatement(SQL_DELETE);
            ps.setInt(1, c.getIdCarrera());
            ps.executeUpdate();
        } finally {
            if (ps != null) ps.close();
            if (conexion != null) conexion.close();
        }
    }

    // ---------- readAll ----------
    public List<Carrera> readAll() throws SQLException {
        obtenerConexion();
        PreparedStatement ps = null;
        ResultSet rs = null;
        List<Carrera> resultados = null;
        try {
            ps = conexion.prepareStatement(SQL_SELECT_ALL);
            rs = ps.executeQuery();
            resultados = obtenerResultados(rs);
            if (resultados.size() > 0) {
                return resultados;
            } else {
                return null;
            }
        } finally {
            if (rs != null) rs.close();
            if (ps != null) ps.close();
            if (conexion != null) conexion.close();
        }
    }

    // ---------- read ----------
    public Carrera read(Carrera c) throws SQLException {
        obtenerConexion();
        PreparedStatement ps = null;
        ResultSet rs = null;
        List<Carrera> resultados = null;
        try {
            ps = conexion.prepareStatement(SQL_SELECT);
            ps.setInt(1, c.getIdCarrera());
            rs = ps.executeQuery();
            resultados = obtenerResultados(rs);
            if (resultados.size() > 0) {
                return resultados.get(0);
            } else {
                return null;
            }
        } finally {
            if (rs != null) rs.close();
            if (ps != null) ps.close();
            if (conexion != null) conexion.close();
        }
    }

    // ---------- auxiliar ----------
    private List<Carrera> obtenerResultados(ResultSet rs) throws SQLException {
        List<Carrera> r = new ArrayList<>();
        while (rs.next()) {
            Carrera c = new Carrera();
            c.setIdCarrera(rs.getInt("idCarrera"));
            c.setNombreCarrera(rs.getString("nombreCarrera"));
            c.setDescripcionCarrera(rs.getString("descripcionCarrera"));
            r.add(c);
        }
        return r;
    }

Tres diferencias entre esta versión y lo que quedó en el pizarrón

No son correcciones a lo que él dijo: son los cabos que dejó sueltos a propósito por tiempo, y conviene que sepas cuáles son.

  • Las listas van tipadas (List<Carrera>). Él las dejó genéricas y dijo explícitamente "ustedes determinen si es una lista tipada o no". Tipadas te ahorran los casts y los errores en tiempo de ejecución.
  • obtenerConexion() declara sus excepciones en vez de atraparlas con printStackTrace(). Es coherente con la estafeta que él mismo explicó: si la conexión falla, el método no debería seguir como si nada.
  • read() usa SQL_SELECT, el que lleva WHERE. Es fácil dejar pegado el SQL_SELECT_ALL al copiar el método de arriba, y el síntoma es feo: te devuelve la primera carrera de la tabla en vez de la que pediste, sin lanzar ningún error.

Sobre lo que sí quedó pendiente de verdad: el create() no recupera el id que generó la base, y el delete() ignora el número de filas afectadas. Los dos temas salieron en clase pero no se resolvieron en código.
